# 为 AI Agent 编写有效工具

**非官方译文。** 官方原文：[Writing effective tools for agents — with agents](https://www.anthropic.com/engineering/writing-tools-for-agents)（Anthropic · Engineering）。

## 导读

工具不是给另一个程序用的函数，而是给会犹豫、会选错、上下文有限的 Agent 用的契约。这篇适合已经接上 MCP、发现模型选错工具或被返回淹没的人。做法是：先做原型和评测，再让 Agent 一起改工具。原则覆盖选什么做、命名空间、高信号返回、省 token，以及描述本身的提示词工程。

原文发表于 2025 年 9 月 11 日。文中脚注说明：这些技术是在训练底层 LLM 之外的改进。

## 译文

MCP（Model Context Protocol，模型上下文协议）可以让 LLM Agent 拥有潜在数百个工具去解决真实任务。但怎样让这些工具尽可能有效？

这篇描述他们在多种智能体式 AI 系统里提升表现最有效的技术。

先讲你可以怎么做：

- 构建并测试工具原型
- 和 Agent 一起，对工具做全面评测并跑起来
- 与 Claude Code 这类 Agent 协作，自动提高工具表现

最后归纳沿途识别出的高质量工具原则：

- 选择该实现（以及不该实现）的工具
- 用命名空间划清功能边界
- 从工具向 Agent 返回有意义的上下文
- 为 token 效率优化工具响应
- 对工具描述和规格做提示词工程

做出评测，才能系统测量工具表现。可以用 Claude Code 对着这份评测自动优化工具。

图：有了评测，就可以系统测量工具表现，并用 Claude Code 对着评测自动优化。图见[原文](https://www.anthropic.com/engineering/writing-tools-for-agents)。

### 什么是工具

在计算里，确定系统在相同输入下每次给出相同输出；非确定系统——比如 Agent——即使起点相同，也可能给出不同响应。

传统写软件，是在确定系统之间立契约。例如 `getWeather("NYC")` 每次都会以完全相同的方式去取纽约市的天气。

工具是一种新软件：它反映的是确定系统与非确定 Agent 之间的契约。用户问「今天该带伞吗？」，Agent 可能调用天气工具，可能凭一般知识回答，甚至可能先追问地点。偶尔，Agent 还会幻觉，或根本没弄懂怎么用工具。

因此，为 Agent 写软件要从根本上重新想：不要按给其他开发者或系统写函数和 API 的方式去写工具和 MCP 服务器，而要为 Agent 来设计。

目标是扩大 Agent 能有效解决广泛任务的表面积：用工具去追求多种成功策略。经验上，对 Agent 最「顺手」的工具，对人来说也出奇地直观。

### 如何编写工具

这一节讲如何与 Agent 协作，既写出工具，也改进交给它们的工具。先把工具的快速原型立起来，在本地测试。接着跑全面评测，测量后续改动。和 Agent 一起，重复评估和改进，直到 Agent 在真实任务上表现强。

#### 做原型

不自己上手，很难预料哪些工具 Agent 觉得顺手、哪些不顺手。先立一个快速原型。如果用 Claude Code 写工具（甚至可能一次写成），把工具会依赖的软件库、API 或 SDK（包括 MCP SDK）的文档给 Claude 会有帮助。对 LLM 友好的文档常常以扁平的 `llms.txt` 出现在官方文档站（他们的 API 也有）。

把工具包进本地 MCP 服务器或 Desktop extension（DXT），就可以在 Claude Code 或 Claude Desktop 里连接并测试。

把本地 MCP 服务器接到 Claude Code：运行 `claude mcp add [args...]`。

接到 Claude Desktop：分别到 `Settings > Developer` 或 `Settings > Extensions`。

工具也可以直接传进 Anthropic API 调用，做程序化测试。

自己把工具试一遍，找出毛边。收集用户反馈，对你期望工具能支撑的用例和提示建立直觉。

#### 跑评测

接下来要测量 Claude 用你的工具用得怎么样，方法是跑评测。先生成大量扎根于真实用途的评测任务。建议和 Agent 协作，分析结果并决定如何改进工具。端到端过程见他们的工具评测 cookbook。

图：内部 Slack 工具在留出测试集上的表现。图见[原文](https://www.anthropic.com/engineering/writing-tools-for-agents)。

**生成评测任务**

有了早期原型，Claude Code 可以很快探索工具，并造出几十对提示和响应。提示应来自真实用途，基于真实的数据源和服务（例如内部知识库和微服务）。建议避免过于简单、表面的「沙箱」环境，它们对工具的压力不够。强的评测任务可能需要多次工具调用——潜在几十次。

强任务的例子：

- 下周和 Jane 约一场会，讨论我们最新的 Acme Corp 项目。附上上次项目规划会的笔记，并预订会议室。
- 客户 ID 9182 报告同一次购买被扣了三次款。找出所有相关日志，判断是否还有其他客户受同一问题影响。
- 客户 Sarah Chen 刚提交取消请求。准备一份挽留方案。确定：（1）他们为什么离开，（2）什么挽留方案最有吸引力，（3）提出方案前应留意的风险。

较弱的任务：

- 下周和 jane@acme.corp 约一场会。
- 在支付日志里搜 `purchase_complete` 和 `customer_id=9182`。
- 找出客户 ID 45892 的取消请求。

每条评测提示都应配上可验证的响应或结果。验证器可以简单到地面真值与采样响应的精确字符串比较，也可以复杂到让 Claude 来评判。避免过严的验证器：因为格式、标点或同样正确的另一种说法，就把正确响应拒掉。

对每一对提示和响应，还可以选择写明你期望 Agent 在解题时调用的工具，用来测量评测中 Agent 是否抓住了每个工具的用途。但正确解题可能有多条路，尽量不要过度规定或过拟合到某一种策略。

**跑评测**

建议用直接的 LLM API 调用，程序化地跑评测。用简单的智能体循环（`while` 循环包住交替的 LLM API 调用和工具调用）：每个评测任务一个循环。每个评测 Agent 只拿到一条任务提示和你的工具。

在评测 Agent 的系统提示里，建议让它们不只输出结构化响应块（供验证），也输出推理和反馈块。让这些块出现在工具调用和响应块之前，可能通过触发思维链（chain-of-thought，CoT）来提高 LLM 的有效智能。

如果用 Claude 跑评测，可以打开交错思考（interleaved thinking），获得类似的「开箱即用」功能。这有助于探查 Agent 为什么调用或不调用某些工具，并标出工具描述和规格里具体可改进的地方。

除了顶层准确率，建议收集其他指标：单次工具调用和任务的总运行时间、工具调用总次数、总 token 消耗、工具错误。跟踪工具调用能揭示 Agent 常走的工作流，也给工具合并提供机会。

图：内部 Asana 工具在留出测试集上的表现。图见[原文](https://www.anthropic.com/engineering/writing-tools-for-agents)。

**分析结果**

Agent 是发现问题和提供反馈的帮手，从互相矛盾的工具描述，到低效实现和令人困惑的工具 schema。但要记住：Agent 在反馈和响应里省略的，常常比它写出来的更重要。LLM 并不总是说出它的意思。

观察 Agent 在哪里卡住或困惑。通读评测 Agent 的推理和反馈（或 CoT），找出毛边。复查原始记录（包括工具调用和工具响应），抓住 CoT 里没有明说的行为。要读字里行间：评测 Agent 不一定知道正确答案和策略。

分析工具调用指标。大量冗余调用，可能说明分页或 token 上限参数需要调整；大量因无效参数导致的工具错误，可能说明工具需要更清楚的描述或更好的示例。他们推出 Claude 的网页搜索工具时，发现 Claude 会不必要地把 `2025` 追加到工具的 `query` 参数上，使搜索结果偏掉、表现下降（他们通过改进工具描述把 Claude 拉回正轨）。

#### 与 Agent 协作

甚至可以让 Agent 分析结果并替你改进工具。把评测 Agent 的记录拼起来，贴进 Claude Code。Claude 擅长分析记录，并一次重构很多工具——例如在做出新改动时，保证工具实现和描述仍然自洽。

事实上，这篇里的大部分建议，来自他们用 Claude Code 反复优化内部工具实现。评测建在内部工作区之上，镜像内部工作流的复杂度，包括真实的项目、文档和消息。

他们依靠留出测试集，确保没有过拟合到「训练」评测上。这些测试集显示：即便超出他们用「专家」工具实现所达到的水平，仍能再挤出性能——无论那些工具是研究员手写的，还是 Claude 自己生成的。

下一节分享从这个过程里学到的一些东西。

### 编写有效工具的原则

#### 为 Agent 选择合适的工具

更多工具并不总是更好的结果。他们观察到的一个常见错误，是工具仅仅包装已有软件功能或 API 端点——不管这些工具对 Agent 是否合适。因为 Agent 有不同于传统软件的「可供性」（affordances），也就是它们感知自己能用这些工具采取哪些行动的方式不同。

LLM Agent 的「上下文」有限（一次能处理的信息有上限），而计算机内存便宜且充裕。考虑在通讯录里找一个联系人。传统程序可以高效地存下联系人列表，一次处理一个，检查完再下一个。

但如果 LLM Agent 用的工具返回全部联系人，然后它得一个 token 一个 token 读过去，就是在用有限的上下文浪费在无关信息上（想象从第一页读到最后一页来找联系人，也就是蛮力搜索）。对 Agent 和人更自然的做法，是先跳到相关的那一页（也许按字母找到）。

建议做少数想清楚的工具，对准具体的高影响工作流，与评测任务匹配，再从那里扩展。通讯录的例子里，可以实现 `search_contacts` 或 `message_contact`，而不是 `list_contacts`。

工具可以合并功能，在底下处理潜在多个离散操作（或 API 调用）。例如，工具可以用相关元数据丰富响应，或在一次工具调用里处理经常串在一起的多步任务。

一些例子：

- 与其实现 `list_users`、`list_events`、`create_event`，不如实现 `schedule_event`：找到空档并安排事件。
- 与其实现 `read_logs`，不如实现 `search_logs`：只返回相关日志行和一点周围上下文。
- 与其实现 `get_customer_by_id`、`list_transactions`、`list_notes`，不如实现 `get_customer_context`：一次汇编某客户最近且相关的信息。

确保每个工具都有清楚、独特的用途。工具应让 Agent 能以人在同样底层资源下会用的方式拆分并解决问题，同时减少原本会被中间输出吃掉的上下文。

工具太多或重叠，也会让 Agent 偏离高效策略。仔细、有选择地规划你建（或不建）的工具，回报很大。

#### 为工具做命名空间

AI Agent 可能会接触几十个 MCP 服务器和数百个不同工具，包括其他开发者做的。工具功能重叠或用途含糊时，Agent 会搞不清该用哪个。

命名空间（把相关工具归到共同前缀下）能帮大量工具划清边界；MCP 客户端有时默认就这么做。例如按服务做命名空间（`asana_search`、`jira_search`），按资源做（`asana_projects_search`、`asana_users_search`），能帮助 Agent 在正确的时间选对工具。

他们发现，前缀式和后缀式命名空间之间的选择，对工具使用评测有不小的影响。效果因 LLM 而异，建议按你自己的评测选择命名方案。

Agent 可能调错工具、用错参数调对工具、调得太少，或错误处理工具响应。有选择地实现那些名字反映任务自然划分的工具，同时减少载入 Agent 上下文的工具数量和描述，并把智能体式计算从上下文卸载回工具调用本身。这降低 Agent 整体犯错的风险。

#### 从工具返回有意义的上下文

同样，工具实现应注意只把高信号信息返回给 Agent。应优先考虑上下文相关性，而不是灵活性，并避开低层技术标识（例如 `uuid`、`256px_image_url`、`mime_type`）。`name`、`image_url`、`file_type` 这类字段，更可能直接告知 Agent 的后续行动和响应。

Agent 处理自然语言名称、术语或标识，通常也比处理晦涩标识成功得多。他们发现：仅仅把任意的字母数字 UUID 解析成更有语义、可解释的语言（甚至一套从 0 开始的 ID），就能显著提高 Claude 在检索任务上的精度，减少幻觉。

有些情况下，Agent 需要同时能和自然语言输出以及技术标识打交道，哪怕只是为了触发下游工具调用（例如 `search_user(name='jane')` → `send_message(id=12345)`）。可以在工具里暴露一个简单的 `response_format` 枚举参数，让 Agent 控制工具返回 `concise` 还是 `detailed`。

还可以加更多格式以获得更大灵活性，类似 GraphQL：你可以精确选择想收到哪些信息。下面是控制工具响应详略的 `ResponseFormat` 枚举示例：

```plaintext
enum ResponseFormat {
   DETAILED = "detailed",
   CONCISE = "concise"
}
```

原文配有一份详细工具响应示例（206 token）和一份简洁工具响应示例（72 token）。图见[原文](https://www.anthropic.com/engineering/writing-tools-for-agents)。

Slack 的帖子和回复由唯一的 `thread_ts` 标识，取回复时必须用它。`thread_ts` 和其他 ID（`channel_id`、`user_id`）可以从 `detailed` 响应里拿到，以便后续需要这些 ID 的工具调用。`concise` 响应只返回帖子内容，不含 ID。这个例子里，`concise` 大约只用三分之一的 token。

连工具响应的结构——例如 XML、JSON 或 Markdown——也会影响评测表现：没有一刀切的方案。因为 LLM 按下一个 token 预测来训练，往往在与训练数据匹配的格式上表现更好。最优结构因任务和 Agent 差别很大。建议按你自己的评测选择最好的响应结构。

#### 为 token 效率优化工具响应

优化上下文的质量很重要，优化返回给 Agent 的上下文数量也同样重要。

对任何可能吃掉大量上下文的工具响应，建议组合使用分页、范围选择、过滤和/或截断，并给出合理的默认参数。对 Claude Code，他们默认把工具响应限制在 25,000 token。他们预期 Agent 的有效上下文长度会随时间增长，但对上下文高效的工具的需求会留下。

如果选择截断响应，一定要用有帮助的指令引导 Agent。可以直接鼓励 Agent 采取更省 token 的策略，例如在知识检索任务上做许多小而准的搜索，而不是一次宽搜索。同样，如果工具调用报错（例如输入校验），可以把错误响应做成提示词工程：清楚传达具体、可执行的改进，而不是不透明的错误码或堆栈。

原文配有截断响应、无帮助的错误响应、有帮助的错误响应三则示例。截断和错误响应可以把 Agent 引向更省 token 的用法（用过滤或分页），或给出格式正确的工具输入示例。图见[原文](https://www.anthropic.com/engineering/writing-tools-for-agents)。

#### 为工具描述做提示词工程

现在到了改进工具最有效的方法之一：对工具描述和规格做提示词工程。因为它们会被载入 Agent 的上下文，可以共同把 Agent 引向有效的工具调用行为。

写工具描述和规格时，想你会对团队里的新员工怎样描述这个工具。把你可能隐含带着的上下文说出来：专门的查询格式、冷僻术语的定义、底层资源之间的关系。用清楚的描述（并用严格的数据模型强制）预期的输入和输出，避免歧义。尤其是输入参数应当命名无歧义：不要叫 `user`，试着叫 `user_id`。

有了评测，就可以更有信心地测量提示词工程的影响。工具描述上很小的打磨，也能带来戏剧性的改进。他们对工具描述做了精确打磨之后，Claude Sonnet 3.5 在 SWE-bench Verified 评测上达到了当时的先进水平，大幅降低错误率并提高任务完成度。

工具定义的其他最佳实践见开发者指南。如果是为 Claude 做工具，也建议读工具如何被动态载入 Claude 系统提示。最后，如果是为 MCP 服务器写工具，工具注解（annotations）有助于披露哪些工具需要开放世界访问，或会做破坏性更改。

### 向前看

要为 Agent 做出有效工具，需要把软件开发实践从可预测的确定模式，重新定向到非确定模式。

通过这篇描述的迭代、由评测驱动的过程，他们识别出工具成功的一致模式：有效的工具被有意地、清楚地定义，审慎使用 Agent 上下文，能在多样的工作流里组合，并让 Agent 能直观地解决真实任务。

未来，他们预期 Agent 与世界交互的具体机制会演化——从 MCP 协议的更新，到底层 LLM 本身的升级。用系统化、由评测驱动的方法改进 Agent 的工具，就可以确保 Agent 变得更强时，它们用的工具也一起演化。

## 笔记

- 「人说不清该用哪个工具，就别指望模型」是这篇最硬的筛选标准，比再写一条描述有用。
- `concise` / `detailed` 和 25,000 token 截断，是把上下文预算写进工具契约，而不是留给模型自己节制。
- 用留出测试集防止过拟合「训练评测」，和后来[拆解 AI Agent 评测](./demystifying-evals-for-ai-agents)里区分能力评测和回归是同一类纪律。
