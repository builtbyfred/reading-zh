# 你的编程 Agent 让你成了经理

**非官方译文。** 原文：[Your coding agents made you a manager](https://x.com/addyosmani/status/2119332146485891501)（Addy Osmani · [@addyosmani](https://x.com/addyosmani) · X Article · 2026-11-08 15:32，上海时间）。

## 导读

整天和编程 Agent 待在一起，就是在做管理：挑任务、写说明、委派、跟进、验收、决定什么可以上线。Addy Osmani 把优秀工程经理的做法，对照他在使用和打造 Claude Code 时形成的习惯。各节大致按影响力排，杠杆最高的是给 Agent 一个能跑的检查。

适合走个人贡献者路径、又不想变成「人肉测试套件」的人。他同时写明这套类比哪里不成立：返工几乎免费，Agent 太容易附和，管 Agent 的技能也不会反向变成带人的能力。文中的产品细节以 Claude Code 为准。

## 译文

管理 Agent 的技能，基本上就是管理团队的技能，而且你不需要当经理也能学会。

如果你整天都在和编程 Agent 打交道，你就是在做管理。你一遍遍地挑选任务、撰写指令、委派、跟进、评估结果，并决定什么可以上线。从 Agent 身上获益最多的工程师，未必是最擅长提示词工程的人。他们是那些学会了管理的人，不管是有意还是无意。

这个说法可能不太受欢迎。我欣赏的许多工程师选择了个人贡献者（IC）的职业路径，因为他们想离一线工作近一些。他们看到朋友当了经理，然后消失在日程表里。但我不是让你去当那样的经理。我说的「管理」有特定含义：靠促成别人的工作，来做出好结果。我当然也不是说 Agent 可以替代经理或同事。

你对糟糕经理的每一条抱怨，都是一份与 Agent 交互的 bug 报告。想想交接。如果你经历过糟糕的交接，你可能收到过一项感觉含糊、缺少上下文、或者期望一再变动的请求。对 IC 来说好消息是：你多年来一直处在交接的接收端，所以你可能知道好的交接长什么样。

我之前写过，[你的编程 Agent 需要一个经理](https://addyosmani.com/blog/coding-agents-manager/)。我也写过委派里一个不易察觉的风险：[cognitive surrender（认知投降）](https://addyosmani.com/blog/cognitive-surrender/)。这篇文章把优秀工程经理的做法，和我们在使用与打造 Claude Code 过程中学到的东西做了对比。各节大致按影响力排序，杠杆最高的习惯放在最前面。

### 给它一个检查自己工作的办法

**最佳实践**：为 Agent 提供一种验证自己工作的机制，比如测试套件、构建或截图，并让它把结果当作证据展示给你。

**反模式**：把「看起来做完了」当作确认。这会迫使你承担全部验证，变成 Agent 的测试套件。

问一位有经验的经理，他们如何在不用通读一切的情况下，确信团队产出的是好东西。他们会谈到护栏：CI、代码审查、仪表盘、值班，等等。不搭护栏的新手经理最后什么都得自己验证，不出一个季度就成了瓶颈。Agent 也一样。正如 [Claude Code 最佳实践指南](https://code.claude.com/docs/en/best-practices)所解释的，Agent 会在工作看起来完成时停下。如果没有验证，「看起来做完了」就是 Agent 仅有的验证。提供验证机制之后，Agent 可以做完工作、跑验证、看到失败，并自己修正。对 UI 改动来说，这可以是真的在浏览器里打开页面，一直改到它能用、而且好看。

验证机制几乎可以是任何东西，只要它能给出明确的通过或失败。比如测试、构建退出码、linter、diff 脚本和截图。指南指出，跑这些验证的那条命令，是你的 `CLAUDE.md`（Agent 每次会话开始时读取的指令文件）里最有用的一行。有了验证机制，可以这样把它放进工作流：

- **提出要求。**「改完之后跑 auth 测试，一直改到通过为止。」
- **设定目标。**用 `/goal` 时，每一轮之后由另一个模型检查条件是否成立。做长时间的后台工作时最有用。
- **强制执行。**`Stop` hook 可以在类型检查通过之前，阻止这一轮结束。
- **交给审查。**`/code-review` 把 diff 发给一个新的子 Agent（它没看过你们的对话）去审查，就像作者不会批准自己的 PR。

你甚至可以控制审查的范围。如果你让它找问题，它总能找到点什么。如果你让它找正确性问题、忽略代码风格，它就会照做。好的经理学习如何征求反馈，用的也是这个办法。Claude Code 工具箱里的大部分功能，都是为了收紧这个循环。Skill、hook、子 Agent 和 MCP（Model Context Protocol，模型上下文协议）都是为了补上「做事」和「验证」之间的缺口，让你只去关注 Agent 验证不了的部分。这正是有经验的工程经理在做的事。

### 设定清晰的上下文

**最佳实践**：把 Agent 靠查看仓库无法知道的内容写清楚，包括：任务目标以及它为什么重要、约束、不在范围内的事，还有成功标准。

**反模式**：只丢过去一句话的任务，真正的期望留在你脑子里；或者在说明里塞满 Agent 读代码就能发现的东西。

有效的经理会把期望的结果、约束和目标写清楚。他们说明工作应该达成什么，但把「怎么做」留给做事的人。军队里称之为指挥官意图（commander's intent）。Netflix 称之为「给上下文，而不是控制」（context, not control）。

和 Agent 协作的难点在于，很难知道它缺了哪一块上下文。编程 Agent 在每个任务上做的第一件事，就是读你的代码。当前模型非常擅长抓住你的目录结构、约定，以及测试是怎么搭的，而且比你描述它们快得多。

动笔之前，先想 Agent 自己能弄明白什么。如果它能在代码里读到，而且它真的会去读，你就不用说。把文字花在仓库之外的部分，比如一次会议的决定、某人内部的部署流程、这个任务为什么重要，以及这一次「完成」意味着什么。

拿一个含糊的任务「让仪表盘更快」为例，把它改写成提示。这里的数字只是举例。

```bash
Get p95 load time for the /team dashboard under 2s for orgs with 10k+ members.

Why: enterprise admins open it daily, and slow loads are their top support ticket.

Constraints: no schema changes; keep the API response shape.

Out of scope: UI changes; caching the whole page.
Check: run scripts/perf/team.sh and show before and after numbers.
```

> 译注：上面的提示按原文保留，方便直接粘贴。原文把这块标成代码。大意：把成员数 1 万以上的组织的 `/team` 仪表盘 p95 加载时间降到 2 秒以内。原因：企业管理员每天都会打开它，加载慢是他们最多的支持工单。约束：不改 schema；保持 API 响应的形状。不在范围内：UI 改动；把整页缓存起来。检查：运行 `scripts/perf/team.sh`，给出前后的数字。

不是每个任务都要这样写。如果是在做探索，写一句笼统的提示完全没问题，做着再收一收就行。如果你还没准备好写提示，可以让 Agent 来采访你，直到它能写出规格说明；把规格说明存成文件，再开一个新会话，让 Agent 照着它来做。之后你还可以拿这份规格说明来对照审查。

你可能还需要让 Agent 能用上别的工具，比如问题跟踪、错误仪表盘或团队聊天。像对待团队里的新人一样对待你的 Agent。如果是它本来就熟悉的 CLI，比如 `gh`，你通常不用多说什么。

### 让每一次纠正都产生复利

**最佳实践**：同一件事纠正超过一次，就把它写进团队的 `CLAUDE.md`，或者做成共享的 Skill。时间久了，再看新模型是否减少了这类纠正的需要。

**反模式**：每个会话都手动纠正同一件事，或者依赖只存在于你自己机器上的隐性知识。

把 `CLAUDE.md` 用到位的团队，会隔一阵更新一次，并把值得预防的错误写成教训。有些团队甚至在代码审查里写上 `@claude`，把反馈收成一条长期规矩。`CLAUDE.md` 要保持短。适合放进去的是这些：

- 怎么验证一件事（确切的命令）
- 代码里容易让人看错的地方
- 仓库里找不到的那些决定
- 任何你纠正过两次的东西

这些都是书面信息会复利的例子。它比人换团队、模型被换掉都活得更久。

### 让它决定，只强制执行不能变通的事

**最佳实践**：默认让 Agent 自己决定。只对少数必须始终发生、或绝不能发生的事使用硬性强制（例如 hook、deny 规则，也就是拒绝规则）。

**反模式**：用全大写写规则，给可有可无的偏好定义 hook，或者新模型早就不再需要这些习惯，你却还留着旧模型那一套。

Andy Grove 的《格鲁夫给经理人的第一课》（High Output Management）把这称为任务相关成熟度（task-relevant maturity）：监督该有多紧，取决于一个人在这项具体任务上的过往表现，而不是他的整体能力。

给新经理的一条老建议说的是同一件事：给人的自由度比你自己舒服的程度再多一点，同时给他们兜底，也要他们负责。

Claude Code 把这一点讲明了：提示、`CLAUDE.md` 和 Skill 是请求，模型可以考虑，并选择是否照做；hook、deny 规则和托管设置是要求，总会被强制执行。大多数情况下，你希望 Agent 自己拿主意。很多时候，看着真实代码的模型，比你事先写下的规则，更适合判断一条准则在这里适不适用。用强制来设定硬性要求，比如「绝不编辑生成的客户端」，或「始终运行许可证头脚本」。特别是，新的终端和 VS Code 会话会以 auto 模式启动，其中的分类器会滤掉不安全的行为，比如部署到生产环境，或 `force push` 覆盖别人的工作。

指南的建议有两面。如果你把 `CLAUDE.md` 里的某一行强调了又强调，Agent 还是没照做，那它就该成为一个 hook。如果某个 hook 表达的是偏好而不是要求，就该删掉，让 Agent 自己拿主意。这就像团队决定废掉一个不再有用的流程。换了新模型，也要跟着调整。指南列了一份可以停掉的习惯：全大写的指令、「think harder」（努力程度现在是一项设置），以及「don't be lazy」。对当前的模型，这些往往让规则被执行得过死，也让人过度干活。对 Agent 来说，过度的流程就是新的微观管理。

### 先规划，再让它动手

**最佳实践**：在 Agent 开始写代码之前，先有一份双方都同意的计划，读出里面的隐含假设，并把任务拆成互不重叠的并行工作。

**反模式**：让多个 Agent 同时处理互相重叠的任务，然后花一下午去解决合并冲突和重复的决定。

这里一个好的工作流是：先进入 plan mode（计划模式），把计划改到对为止，再把写代码委派出去。计划好的话，模型常常能一次做完。更大的任务，再用第二个会话，像 staff 工程师那样把计划看一遍。这是设计评审，是抓住走错方向成本最低的地方。审计划时要找隐含假设（在一对一里，这就是问「你对什么还不确定？」）。

任务拆解越来越多地交给 Agent。Claude Code 里的 `/batch` 接一项大的机械改动，拆成 5 到 30 个任务，展示计划，在各自的 worktree（隔离工作区，同一仓库的另一份检出）里执行，再为每个任务开一个 PR。你不用再自己把工作切开，只要检查这些切片有没有重叠，并确保共享接口先落地。否则，你可能得到一种虚假的并行。五个 Agent 接过互相重叠的任务，不会带来五倍产出，只会带来一个有五位作者的合并冲突。

### 早纠偏，快重来

**最佳实践**：看住开头一分钟，并引导 Agent。一发现它跑偏就纠正。如果已经两次纠正失败，就开一个新会话，用更好的提示重新开始。

**反模式**：第三次、第四次地去纠正 Agent，而不去改你的要求。

有经验的经理知道，一个能干的人连着失手，问题可能在上游：指令、上下文或范围。Agent 这边说得很明确：一跑偏就按 `Esc`。已经两次纠正失败，就清掉会话，把学到的写进一条更好的提示。第三次纠正，多半只是又一段模型得反复重读、重新处理的信息，其中包括那些失败的尝试。

便宜的回滚也在改写局面。`/rewind` 把代码和对话一起退回更早的节点，于是可以低风险地先试更有野心的做法。好的经理对人也这样：如果撤销错误很便宜，就让他们试有野心的做法。事后做 retro（复盘），适用的话，把修正概括进 `CLAUDE.md`。

### 委派任务，绝不委派判断

**最佳实践**：Agent 做事，你来决定重要的事：产品上的拍板、安全边界、什么可以上线。对待每一份 diff，都像出了问题你会因此被 page（半夜叫起来）。

**反模式**：因为测试是绿的、名字看着合理，就批准大段 diff。这不是代码审查，这是代码追认。

没有经理能说「那是我的下属上的线，不是我」。你跑的每一个 Agent 也一样。我自己就掉进过这个坑。我让一个 Agent 去调研我们和竞品的差距，并写本地 PR 来补上这些差距。我读了调研，扫了一眼代码，差点就推送一批改动：它们给用户增加了复杂度，收益却很小。我委派了工作，也差点把决定一起委派了出去。这个坑很容易掉进去：一份 600 行的 diff，名字看着合理，测试是绿的，批准。

这样分工是合理的：代码风格、lint、审查意见的后续修改、常见 bug 和单元测试交给 Agent；安全边界、合规和产品决策留给人。

协调也是同一回事。Agent 可以记住交接，但在互相冲突的请求之间做取舍、让人真正承诺下来，仍然是人的工作。

你不必待在每一次改动的内环里。你要握住的是那些外环：约束是什么、输出你实际读多少、留下什么证据、什么必须由人签字。改动还要小，因为审查的单位就是理解的单位。

### 设计一次不需要你的运行

**最佳实践**：部署一项自主任务之前，先定义完成、自我验证、边界、护栏和人工批准。

**反模式**：睡前启动一个长时间运行的进程，没有完成的定义，也没有停止点。第二天早上醒来，发现模型整夜都在一个错误前提上干活。

隔级经理（skip-level manager）不管单个工程师手里的活。他们管的是目标、护栏、检查点和负责人这些工作。AI Agent 走的是类似的轨迹。它们已经在把任务的一部分交给子 Agent，也可以按计划、在 CI 失败之后、或在新 PR 打开之后自己跑。前沿是能自己治理的系统：自主启动、自己验证，只在需要做决定时才叫人。

角色从控制会话，转到设计你的循环。设计一次无人值守的运行时，要问自己的五个问题，和一位好经理把项目交给资深工程师、然后自己去休假之前会问的一样：

- **它知道「完成」是什么样吗？**（目标条件、规格文件，或一个失败的测试，它得把它跑绿。）
- **它有自我验证的办法吗？**（测试套件、`Stop` hook，或审查这一步。）
- **它的边界是什么？**（权限控制、沙箱（sandbox）、worktree，或唯一允许它推送的那个分支。）
- **它的护栏是什么？**（轮次上限，或花费上限。）
- **它在哪里交出结果，由谁批准？**（一个 PR 或一份总结，以及对任何不可逆操作的人工批准。）

指南里还有两个经理会认出来的好习惯。一是试点：先让批处理在三个文件上跑，改提示，再跑剩下的。二是任何新东西，在你放心让它无人值守之前，先看最初几次运行。把它想成试用期。

### 扩展验证，而不是注意力

**最佳实践**：扩大 Agent 用量的速度，不要超过检查、目标和带着新上下文的审查者接手监看的速度，并且在吞吐量之外也衡量质量。

**反模式**：开的会话多到你审不好，并用 AI 写了多少代码来衡量成功。

经理很快就会摸清自己的管理幅度。直接下属超过某个数量，每个人分到的经理就变少，质量跟着下降。Agent 也一样。这就是我所说的 orchestration tax（编排税）：过了最初几个 Agent，每多一个都比上一个更占你的注意力。大多数日子我会跑四五个后台 Agent，再加几个本地会话，有些日子这已经太多了。

管很多会话，靠的不是高度专注，而是把大部分监看交给自我评估、目标和带着新上下文的审查者，把注意力留给决定。用通知代替轮询，并有一个后台任务的集中视图，也会有帮助。Agent 的数量没法靠你盯得更多来扩大，只能靠需要盯的东西变少。然后衡量系统，而不是衡量活动。有用的指标包括 PR 的周期时间、新员工的上手时间，以及 revert（回退）或返工的频率。衡量 AI 编写代码的占比不是有用的目标，因为你要的是质量和可靠性。Grove 用对冲指标来衡量的规矩在这里适用：如果你衡量合并的 PR 数量，也要衡量回退和返工。

### 决定不去建什么

**最佳实践**：问清楚谁需要它、你怎么知道它奏效了、什么情况会让你停手，并限制 WIP（在制品）。

**反模式**：把每个看似合理的想法都丢进 PR；反正做起来便宜。结果你得到一个团队还得审查、补上安全、再维护的杂物抽屉。

经理说出的最重要的词，往往是「不」。有了 Agent，说「不」更难。开工几乎不花钱，午饭前你就能把任何看似合理的想法丢进一个 PR。但你随即会有一堆 PR，团队得审查、补上安全、支持和维护。现在稀缺的是审查和验证。

事实上，那些老的管理问题现在比以前更要紧。谁提的？我们怎么衡量成功？我们怎么知道该停？如果做起来很便宜，难的问题就不是「我们能不能」，而是「我们该不该」。

### 类比在哪里失效

**最佳实践**：照着管理的最佳实践做，但要算上 Agent 这种对象和人不一样的地方，比如返工便宜、它们很容易附和，以及强项随每次模型发布而变。

**反模式**：把 Agent 当成初级开发者，或者因为你能跑五个 Agent，就觉得自己准备好管理五个人了。

这个类比有用，但不完美。这件事做得最好的人，清楚它不完美在哪里：

- **管理人更难，而且技能不会反向迁移。**你跑过五个 Agent，并不等于你准备好管理五个人。动力、冲突、职业发展，或者长达数月的信任，在 Agent 这里都没有对应物。
- **返工几乎免费。**你可以要求 Agent 做你永远不会要求一个人做的事。白板上起了技术争论，Agent 可以把两三个方案都做出来，让你比较。
- **Agent 没有经验，只有一个笔记本。**auto memory（自动记忆）只在一台机器上记笔记，不会进队友的会话。那不是你整个职业生涯积累的经验和判断。这些教训得写下来，给整个团队。
- **Agent 热情，而且自信。**你让一个好工程师去做错的事，他会顶回来。Agent 更可能照你说的做，而你很容易过度信任它们。在沃顿关于认知投降的研究里，参与者大多数时候接受了错误的 AI 答案，而且变得更自信。你可以让 Agent 反驳它自己的答案，来对冲这种过度自信。
- **你只有一种 Agent 原型，而且它每几个月就变一次。**人的团队有多样的技能和强项。你所有的 Agent 强项和弱点都一样，并且随每次模型发布而变。
- **你仍然要培养初级开发者。**Agent 接走了初级开发者用来学这门手艺基本功的入门活之后，作为经理，你得有意识地替他们把这些练习补上。
- **人的团队仍然重要。**有时你管了一整天 Agent，却没意识到自己挤掉了建设一个有凝聚力的团队所需的时间。别这样。

### 你不需要那个头衔

**最佳实践**：把力气用在让好软件发生上：把上下文设好、把完成定义好、认真审查。

**反模式**：一边跑着交代不清、也没人检查的 Agent，一边用代码行数评价自己。

好的 staff 工程师一直就是这样。他们写设计文档。他们设定上下文。他们做彻底的审查。他们让身边的人变得更好。Agent 让所有工程师从第一天起就能这样做。它们给你上一堂管理速成课。反馈在几分钟里回来，而不是几个季度。你可以撤销自己的错误。这份工作越来越不是自己去写代码，而是成为好代码被写出来的原因。

没有人天生是伟大的经理，也没有人天生是伟大的工程师。你还是靠练习来练出这些技能，和以前一样。但有了 Agent，练习很便宜。

试试这些想法：

- 每项任务都要有一个它能跑的检查。向它要证据。
- 告诉 Agent 它看不见的，省掉它看得见的。
- 写代码之前，先把计划谈清楚。
- 同一件事纠正了两次？记进 `CLAUDE.md`。重复的工作流？做成 Skill。
- 两次纠正都失败了？重新开始，把提示换个说法。
- 审查 diff 时，就当出了问题你会半夜被叫起来。

你不必想当经理。但在 Agent 上做得好的工程师，会在一路上学会管理。
