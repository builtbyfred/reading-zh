# AI Agent 的有效上下文工程

**非官方译文。** 官方原文：[Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)（Anthropic · Engineering）。

## 导读

提示词工程问的是「这句话怎么写」。上下文工程问的是：这一次推理，窗口里到底放哪些 token。适合已经在做多轮 Agent、发现窗口一长模型就飘的人。文中的注意力预算、JIT（即时加载）、compaction（上下文压缩）和子 Agent，是后面写工具、Skill 和长时运行任务的共同背景。

原文发表于 2025 年 9 月 29 日，作者为 Applied AI 团队。

## 译文

应用 AI 里，提示词工程热了几年之后，一个新词变得突出：上下文工程。用语言模型做系统，越来越不是为提示找对词句，而是回答一个更宽的问题：怎样配置上下文，才最可能让模型做出我们要的行为？

上下文指的是从大语言模型采样时放进去的那一组 token。工程问题是：在模型固有约束下，优化这些 token 的效用，从而稳定地得到想要的结果。要把 LLM 用顺，往往得按上下文来想：任一时刻模型能看到的整体状态是什么，这个状态可能引出什么行为。

这篇探讨正在成形的上下文工程，并给出一个更清楚的心智模型，用来做可驾驭、有效的 Agent。

### 上下文工程与提示词工程

在 Anthropic，上下文工程被看成提示词工程的自然延伸。提示词工程是为了更好的结果而书写、组织 LLM 指令的方法（概述和策略见他们的文档）。上下文工程则是在推理期间策划并维持最优 token 集合的一整套策略，包括提示之外也可能落进窗口的所有信息。

早期用 LLM 做工程时，提示是 AI 工程里最大的一块：日常聊天之外，多数用例是为一次性分类或文本生成优化提示。顾名思义，提示词工程的重点是如何写出有效提示，尤其是系统提示。但当我们走向能跨多轮推理、更长时间跨度运行的 Agent，就需要管理整个上下文状态的策略：系统指令、工具、MCP（Model Context Protocol，模型上下文协议）、外部数据、消息历史，等等。

在循环里跑的 Agent 会不断产生可能对下一轮有用的数据，这些信息必须循环地被精炼。上下文工程是一门手艺，也是一门科学：从那个不断变化的可能信息宇宙里，挑出要放进有限窗口的部分。

和「写一条提示」这种离散任务不同，上下文工程是迭代的。每次决定传什么给模型，策划都要发生一次。

### 为什么上下文工程对做好 Agent 很重要

尽管模型很快、也能处理越来越大的数据量，他们观察到：LLM 和人一样，到某个点会失焦或混乱。大海捞针式的基准揭示了 context rot（上下文腐烂）：窗口里的 token 变多，模型从这段上下文里准确回忆信息的能力就下降。

有的模型退化更缓，但这是所有模型都会出现的特性。因此上下文必须被当成收益递减的有限资源。人的工作记忆有限，LLM 也有一份解析大量上下文时要动用的「注意力预算」。每多一个 token，都会消耗这份预算，于是更需要仔细挑选给模型的 token。

注意力稀缺来自架构约束。LLM 基于 transformer：每个 token 都能关注整个上下文里的其他 token，n 个 token 就有 n² 对关系。

上下文变长时，模型捕捉这些成对关系的能力被摊薄，上下文大小和注意力焦点之间出现天然张力。此外，模型的注意力模式来自训练数据分布，短序列通常比长序列更常见。这意味着模型对跨整个上下文的依赖经验更少，专用参数也更少。

位置编码插值等技术让模型能处理更长序列：把长序列适配到原先训练的较短上下文上，但 token 位置理解会有所下降。这些因素造成的是性能梯度，不是硬悬崖：模型在更长上下文里仍然很能干，但相对短上下文，信息检索和长程推理的精度可能下降。

因此，要做出能干的 Agent，认真的上下文工程是必要的。

### 有效上下文的解剖

既然 LLM 受有限注意力预算约束，好的上下文工程就是找到最小的一组高信号 token，使某个期望结果的可能性最大。做起来比说起来难。下面按上下文的不同成分，说明这条原则在实践里是什么意思。

系统提示应当极其清楚，用简单、直接的语言，把想法放在对 Agent 合适的「高度」上。合适的高度是两种常见失败之间的中间地带。一端是工程师把复杂、易碎的逻辑硬编码进提示，以求精确的智能体行为。这会变脆，维护成本随时间上升。另一端是只给模糊的高层指引，既没有具体信号，又错误地假设存在共享上下文。最优高度要平衡：具体到能有效引导行为，又灵活到能给模型强的启发式。

图：光谱的一端是易碎的 if-else 硬编码提示，另一端是过于笼统、或错误假设共享上下文的提示。图见[原文](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)。

建议把提示分成清晰的小节（例如 `<background_information>`、工具指引、输出描述等），并用 XML 标签或 Markdown 标题分开。随着模型变强，提示的精确格式可能没那么重要了。

无论怎么组织系统提示，都应追求能完整勾勒期望行为的最小信息集。（最小不一定等于短：仍要事先给足信息，让 Agent 遵守期望行为。）最好先用手头最强的模型试一个最小提示，看它在任务上的表现，再根据最初测试里的失败模式，补上清楚的指令和示例。

工具让 Agent 与环境互动，并在工作中拉入新的上下文。工具定义了 Agent 与其信息、行动空间之间的契约，因此工具必须促进效率：返回的信息要省 token，也要鼓励高效的 Agent 行为。

在《Writing tools for AI agents – with AI agents》里，他们讨论了如何做出 LLM 容易理解、功能重叠最小的工具。和设计良好的代码库里的函数一样，工具应当自包含、对错误稳健、用途极其清楚。输入参数同样应当描述充分、无歧义，并发挥模型固有的长处。

最常见的失败之一，是工具集臃肿：覆盖的功能太多，或让「该用哪个工具」变得含糊。如果人类工程师都不能确定某个情境该用哪个工具，就不能指望 AI Agent 做得更好。后文会谈到：为 Agent 策划一套最小可行工具集，也有助于在长交互里更可靠地维护和修剪上下文。

提供示例，也就是 few-shot prompting，仍是他们强烈建议的做法。但团队常常把一长串边界情况塞进提示，试图说清 LLM 在某任务上应遵守的每一条规则。他们不建议这样做。应当策划一组多样、典型的示例，有效刻画 Agent 的期望行为。对 LLM 来说，示例是「一张抵一千字的图」。

对各成分（系统提示、工具、示例、消息历史等）的总建议是：用心，让上下文有信息量，同时保持紧。接下来谈运行时动态取回上下文。

### 上下文检索与智能体式搜索

在《Building effective AI agents》里，他们强调了基于 LLM 的工作流和 Agent 的差别。写完那篇之后，他们倾向一个简单定义：Agent 就是在循环里自主使用工具的 LLM。

和客户一起工作时，他们看到这个领域正在收敛到这个简单范式。底层模型更强，Agent 的自主程度就可以提高：更聪明的模型让 Agent 能独立穿越微妙的问题空间，并从错误中恢复。

工程师如何为 Agent 设计上下文，也在转变。今天很多 AI 原生应用在推理前用某种基于嵌入的检索，把重要上下文浮出来供 Agent 推理。随着做法更偏 Agent，他们越来越多地看到团队用「即时」上下文策略来增强这些检索系统。

JIT（即时加载，just-in-time）不是事先处理所有相关数据，而是让 Agent 持有轻量标识（文件路径、存好的查询、网页链接等），运行时再用工具按这些引用把数据动态载入上下文。Anthropic 的智能体式编程方案 Claude Code 用这个办法，在大型数据库上做复杂数据分析。模型可以写有针对性的查询、存结果，并用 `head`、`tail` 这类 Bash 命令分析大量数据，而不必把完整数据对象载入上下文。这接近人的认知：我们一般不把整库信息背下来，而是用文件系统、收件箱、书签这类外部组织和索引，按需取回相关信息。

除了存储效率，这些引用的元数据也能高效地细化行为，无论是显式给出还是直觉上能读出来。对在文件系统里工作的 Agent 来说，`tests` 文件夹里一个叫 `test_utils.py` 的文件，和 `src/core_logic/` 里同名文件，用途不同。目录层级、命名约定和时间戳，都是帮人和 Agent 理解何时、如何使用信息的重要信号。

让 Agent 自主导航并取回数据，也实现了渐进披露：Agent 通过探索逐步发现相关上下文。每次交互都产生指导下一次决策的上下文：文件大小暗示复杂度，命名暗示用途，时间戳可以代理相关性。Agent 可以一层层组装理解，工作记忆里只留必要的，并用记笔记来额外持久化。这种自己管理的上下文窗口，让 Agent 聚焦相关子集，而不是淹没在详尽但可能无关的信息里。

当然有取舍：运行时探索比取回预先算好的数据慢。而且还需要有主见、想清楚的工程，确保 LLM 有合适的工具和启发式去导航信息地形。没有恰当引导，Agent 会误用工具、追进死胡同、或找不到关键信息，从而浪费上下文。

在某些设定里，最有效的 Agent 可能采用混合策略：事先取回一些数据以求速度，再按自己的判断继续自主探索。自主程度的分界取决于任务。Claude Code 就是这种混合：`CLAUDE.md` 会事先被放进上下文，而 glob、grep 这类原语让它能导航环境并即时取回文件，从而绕开过期索引和复杂语法树的问题。

混合策略可能更适合内容不那么动态的场景，例如法律或金融工作。随着模型能力提高，Agent 设计会趋向让聪明的模型聪明地行动，人工策划越来越少。进展这么快，「做能工作的最简单的事」对在 Claude 上做 Agent 的团队，很可能仍是最好的建议。

#### 长程任务的上下文工程

长程任务要求 Agent 在一串动作上保持连贯、上下文和目标导向行为，而 token 数会超过 LLM 的上下文窗口。跨数十分钟到数小时的连续工作，例如大规模代码库迁移或全面的研究项目，需要专门技术来绕开窗口大小的限制。

等更大的窗口似乎是明显的办法。但在可预见的未来，无论窗口多大，只要想要最强的 Agent 表现，都仍会碰到上下文污染和信息相关性问题。为了让 Agent 在更长时间跨度上有效工作，他们发展了几种直接对付这些约束的技术：compaction、结构化笔记，以及多 Agent 架构。

#### Compaction

compaction（上下文压缩）是：对话接近窗口上限时，总结其内容，再用这份总结重新开启一个上下文窗口。它通常是上下文工程里推动长期连贯的第一根杠杆。核心是高保真地蒸馏窗口内容，让 Agent 能以最小的性能下降继续。

例如在 Claude Code 里，他们把消息历史交给模型去总结，压缩最关键的细节。模型保留架构决策、未解决的 bug 和实现细节，丢掉冗余的工具输出或消息。Agent 然后带着这份压缩后的上下文，加上最近访问的五个文件继续。用户得到连续性，而不必担心窗口限制。

compaction 的手艺在于选什么留下、什么丢掉。压得太狠，会丢掉当时不起眼、后来才显出关键的上下文。实现 compaction 的工程师，建议在复杂的 Agent 轨迹上仔细调提示。先把召回做到最大，确保压缩提示抓住轨迹里每一条相关信息，再迭代提高精度，去掉多余内容。

容易下手的多余内容，是清掉工具调用和结果：工具在消息历史深处已经被调用过，Agent 为什么还要再看原始结果？最安全、动手最轻的一种 compaction，是清除工具结果。这最近已作为 Claude Developer Platform 上的一项功能推出。

#### 结构化笔记

结构化笔记，或称 agentic memory（智能体记忆），是 Agent 定期把笔记写到上下文窗口之外的记忆里，以后再拉回窗口。

这个策略用很小的开销提供持久记忆。像 Claude Code 建待办清单，或你的自定义 Agent 维护一份 `NOTES.md`，这种简单模式让 Agent 能跨复杂任务跟踪进度，保住否则会在几十次工具调用之间丢掉的关键上下文和依赖。

Claude 玩宝可梦，展示了记忆如何在非编码领域改变 Agent 的能力。Agent 在数千步游戏里保持精确计数，例如跟踪「过去 1,234 步我一直在 1 号道路训练宝可梦，皮卡丘已经升了 8 级，目标是 10 级」。没有人提示记忆结构，它就会画出探索过的区域、记住已解锁的关键成就，并记下战斗策略，学会哪种攻击对不同对手最有效。

上下文重置之后，Agent 读自己的笔记，继续多小时的训练或迷宫探索。这种跨总结步骤的连贯，使只把信息放在 LLM 窗口里不可能实现的长程策略成为可能。

作为 Sonnet 4.5 发布的一部分，他们在 Claude Developer Platform 上以公开 beta 发布了记忆工具，用基于文件的系统，更容易在窗口之外存储和查阅信息。Agent 可以随时间积累知识库、跨会话维持项目状态、引用先前工作，而不必把一切留在上下文里。

#### 子 Agent 架构

子 Agent 架构是绕开上下文限制的另一条路。不是一个 Agent 试图维持整个项目的状态，而是专门的子 Agent 用干净的窗口处理聚焦的任务。主 Agent 用高层计划来协调，子 Agent 做深入的技术工作，或用工具寻找相关信息。每个子 Agent 可能广泛探索，用掉数万甚至更多 token，但只交回一份浓缩、蒸馏过的工作摘要（常常是 1,000–2,000 token）。

这样关注点分离得很清楚：详细的搜索上下文留在子 Agent 里，主 Agent 专注综合和分析结果。这个模式在《How we built our multi-agent research system》里讨论过，在复杂研究任务上相对单 Agent 系统有实质改进。

选哪种做法取决于任务特点。例如：

- compaction 适合需要大量来回的任务，维持对话流；
- 记笔记适合有清晰里程碑的迭代开发；
- 多 Agent 架构适合并行探索能带来收益的复杂研究与分析。

即便模型继续变好，在更长交互里保持连贯，仍将是做出更有效 Agent 的核心挑战。

### 结论

上下文工程代表我们用 LLM 构建方式的根本转变。模型更强之后，挑战不只是写出完美提示，而是在每一步用心策划进入模型有限注意力预算的信息。无论你是在为长程任务做 compaction、设计省 token 的工具，还是让 Agent 即时探索环境，指导原则相同：找到最小的一组高信号 token，使期望结果的可能性最大。

这些技术会随模型改进继续演化。他们已经看到：更聪明的模型需要更少规定性的工程，Agent 可以更自主地运行。但即便能力上升，把上下文当成珍贵、有限的资源，仍将是做出可靠、有效 Agent 的核心。

可以在 Claude Developer Platform 上开始做上下文工程，并通过记忆与上下文管理 cookbook 获取技巧和最佳实践。
