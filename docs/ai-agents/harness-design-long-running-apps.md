# 长时运行应用的 Harness 设计

**非官方译文。** 官方原文：[Harness design for long-running application development](https://www.anthropic.com/engineering/harness-design-long-running-apps)（Anthropic · Engineering）。

## 导读

长时运行的应用开发里，模型会在上下文变满时失去连贯，也会给自己的产出打高分。这篇用规划者、生成者、评估者三个 Agent 把这两件事拆开：规划者把一两句话扩成产品规格，生成者按 sprint（冲刺）实现，评估者用 Playwright 真的点进页面再打分。前半先在前端设计上把「好不好看」写成可评分标准，后半把同一套生成–评估循环用到全栈，并在 Opus 4.6 上拆掉不再必要的 sprint。

原文发表于 2026 年 3 月 24 日。正文是第一人称实验记录，页上未单列作者姓名。

## 译文

过去几个月，我在做两个彼此相连的问题：让 Claude 做出高质量的前端设计，以及让它在没有人插手的情况下做出完整应用。这项工作起于更早的[前端设计 Skill](https://github.com/anthropics/claude-code/blob/main/plugins/frontend-design/skills/frontend-design/SKILL.md)和[长时运行编码 Agent harness](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)。同事和我当时能靠提示词工程和 harness（任务脚手架）设计，把 Claude 的表现拉到基线之上不少——但两边最后都碰到了天花板。

为了突破，我去找能同时成立于两个很不一样的领域的新 AI 工程做法：一个由主观品味定义，另一个由可核验的正确性和可用性定义。从[生成对抗网络（GAN）](https://en.wikipedia.org/wiki/Generative_adversarial_network)得到启发，我设计了一个生成者 Agent 加评估者 Agent 的多 Agent 结构。要做一个能可靠打分、而且有品味的评估者，得先有一套标准，把「这个设计好吗」这类主观判断变成具体、可打分的说法。

然后我把这些技术用到长时自主编码上，带上了早先 harness 工作里的两条教训：把构建拆成做得到的块，并用结构化产物在会话之间交接上下文。最后的结果是一个三 Agent 架构——规划者、生成者、评估者——在长达数小时的自主编码会话里做出内容丰富的全栈应用。

### 为什么朴素实现不够

我们先前已经表明，harness 设计对长时运行的智能体式编码效果有实质影响。在更早的一次[实验](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)里，我们用一个初始化 Agent 把产品规格拆成任务列表，再用一个编码 Agent 一次实现一个功能，然后交出产物，把上下文带到下一个会话。更广的开发者社区汇合到了相近的认识，例如 [“Ralph Wiggum” 方法](https://ghuntley.com/ralph/)用钩子或脚本让 Agent 停在持续迭代的循环里。

但有些问题一直在。任务更复杂时，Agent 仍会随时间脱轨。把这个问题拆开，我们观察到 Agent 执行这类任务时两种常见失败模式。

第一种是：上下文窗口被填满时，模型容易在长任务上失去连贯（见我们关于[上下文工程](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)的文章）。有些模型还会表现出「上下文焦虑」（context anxiety）：它们以为自己快到上下文上限时，就开始提前收尾。上下文重置能同时处理这两件事：把上下文窗口整个清空，启动一个新的 Agent，并用一份结构化交接带上前一个 Agent 的状态和下一步。

这和 compaction（上下文压缩）不同。压缩是把对话较早的部分就地摘要，让同一个 Agent 在缩短后的历史上继续。压缩保住了连续性，但没有给 Agent 一块干净的白板，上下文焦虑因此仍可能留下。重置给的是干净白板，代价是交接产物里要有足够状态，下一个 Agent 才能干净地接上工作。在我们更早的测试里，Claude Sonnet 4.5 的上下文焦虑强到单靠压缩不足以支撑好的长任务表现，所以上下文重置变成 harness 设计里必不可少的一块。这解决了核心问题，但给每次 harness 运行加上了编排复杂度、token 开销和延迟。

第二个问题是我们先前没有处理过的：自我评估。被要求评估自己刚做出的东西时，Agent 倾向于自信地称赞它——即便在人类观察者看来，质量明显平庸。这个问题在设计这类主观任务上特别突出，因为没有等价于可核验软件测试的二元检查。版面显得精致还是泛泛，是判断题，而 Agent 给自己的作品打分时可靠地偏正。

即便在确有可核验结果的任务上，Agent 有时仍会表现出妨碍它完成任务的糟糕判断。把干活的 Agent 和评判的 Agent 分开，是处理这个问题的一根有力杠杆。分开本身不会立刻消除那种宽容：评估者仍是一个 LLM，倾向于对 LLM 生成的输出慷慨。但把一个独立的评估者调成怀疑的，远比让生成者批判自己的作品可行；一旦有了这份外部反馈，生成者就有具体的东西可以迭代。

### 前端设计：把主观质量变成可评分的

我从前端设计开始实验，自我评估的问题在那里最明显。没有任何干预时，Claude 通常会滑向安全、可预期的版面：技术上能用，视觉上不出奇。

有两点认识塑造了我为前端设计搭的 harness。第一，美学不能完全还原成分数——个人口味总会不同——但可以用编码了设计原则和偏好的评分标准把它往上推。「这个设计美吗」很难一致地回答，但「它是否遵循我们的好设计原则」给了 Claude 具体的东西可打。第二，把前端生成和前端评分分开，可以做出一个反馈环，把生成者推向更强的输出。

据此，我写了四条评分标准，放进生成者和评估者两边的提示里：

- **设计质量**：设计是否像一个连贯的整体，而不是零件的堆砌？这里做得强，意味着颜色、字体、版面、图像和其他细节合在一起，形成明确的情绪和身份。
- **原创性**：看得到定制决策，还是模板版面、库的默认值和 AI 生成套路？人类设计师应当认得出有意的创造性选择。未经修改的现成组件，或 AI 生成的典型迹象（白卡片上的紫色渐变），在这里失败。
- **工艺**：技术执行，包括字体层级、间距一致性、色彩和谐、对比度。这是能力检查，不是创造力检查。多数合理的实现默认就能过；失败意味着基本功坏了。
- **功能性**：与美学无关的可用性。用户能否理解界面在做什么、找到主要操作、不用猜就能完成任务？

我把设计质量和原创性放在工艺和功能性之上。Claude 在工艺和功能性上默认就已经得分不错，所需的技术能力对模型来说往往自然就有。但在设计和原创性上，Claude 的输出常常至多是平淡的。标准明确惩罚高度泛化的 “AI slop”（一眼能认出的生成式套话），并通过把设计和原创性加权更重，把模型推向更多美学上的冒险。

我用带详细分数拆解的 few-shot（少样本）例子校准评估者。这让评估者的判断和我的偏好对齐，并减少迭代之间的分数漂移。

循环搭在 [Claude Agent SDK](https://platform.claude.com/docs/en/agent-sdk/overview) 上，编排因此保持直接。生成者 Agent 先根据用户提示做出一份 HTML/CSS/JS 前端。我给评估者 Playwright MCP，让它在给每条标准打分、写出详细批评之前，直接和活的页面互动。实践里，评估者会自己在页面上导航，截图并仔细研究实现，然后给出评估。这份反馈流回生成者，作为下一次迭代的输入。每次生成我跑 5 到 15 轮迭代，每一轮通常都会在生成者回应评估者批评时，把它推向更有辨识度的方向。因为评估者是在主动浏览页面，而不是给一张静态截图打分，每一轮都要真实的墙上时钟时间。完整运行拉长到最多四小时。我还指示生成者在每次评估之后做一个策略决定：如果分数趋势好，就沿当前方向打磨；如果这条路不行，就转到完全不同的美学。

各次运行里，评估者的评估随迭代变好，然后进入平台期，头上仍有空间。有的生成是增量打磨。有的在迭代之间发生尖锐的美学转向。

标准的措辞以我没有完全预料到的方式牵引生成者。放进「最好的设计是博物馆级别」这类句子，会把设计推向一种特定的视觉汇合，说明和标准绑在一起的提示直接塑造了输出的性格。

分数大体随迭代上升，但模式并不总是干净的线性。后面的实现作为整体往往更好，但我经常更喜欢中间某一轮，而不是最后一轮。实现复杂度也倾向于一轮轮增加，生成者回应评估者的反馈时，会去够更有野心的解法。即便在第一轮，输出也明显好于完全没有提示的基线，说明标准和相关语言本身就在任何评估者反馈带来进一步打磨之前，把模型从泛化默认值上拉开了。

一个突出的例子：我让模型为一个荷兰美术馆做网站。到第九轮，它做出了一个虚构美术馆的干净、深色主题着陆页。页面视觉上打磨过，但大体在我的预期之内。然后在第十轮，它整个放弃这条路，把站点重新想象成一种空间体验：用 CSS 透视渲染的、铺着棋盘格地板的 3D 房间，作品以自由位置挂在墙上，画廊房间之间用门口导航，而不是滚动或点击。这是我在单次生成里以前没见过的那种创造性跳跃。

### 扩展到全栈编码

带着这些发现，我把这套受 GAN 启发的模式用到全栈开发。生成者–评估者循环自然映射到软件开发生命周期：代码审查和 QA 扮演的结构角色，和设计评估者相同。

#### 架构

在早先的[长时运行 harness](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)里，我们用一个初始化 Agent、一个一次做一个功能的编码 Agent，以及会话之间的上下文重置，解决了跨会话仍然连贯的编码。上下文重置是关键的解锁：那套 harness 用的是 Sonnet 4.5，它表现出前面说的「上下文焦虑」。做出一套在上下文重置之间仍然工作良好的 harness，是让模型停在任务上的关键。Opus 4.5 在很大程度上自己去掉了那种行为，于是我可以在这套 harness 里完全丢掉上下文重置。Agent 在整个构建过程中作为一次连续会话运行，沿途由 Claude Agent SDK 的自动 compaction 处理上下文增长。

这项工作在原先 harness 的底座上做成一个三 Agent 系统，每个 Agent 针对我在先前运行里观察到的一个具体缺口。系统包含下面这些 Agent 角色：

**规划者。** 先前的长时运行 harness 要求用户事先给出详细规格。我想把这一步自动化，于是做了一个规划者 Agent：吃下一段 1 到 4 句的简单提示，展开成完整的产品规格。我提示它在范围上要有野心，并停在产品语境和高层技术设计上，而不是详细的技术实现。这个侧重是因为担心：如果规划者事先规定颗粒度很细的技术细节并且写错了，规格里的错误会级联进下游实现。看起来更聪明的做法是约束 Agent 要交出的产物，让它们在干活时自己找出路径。我还要求规划者寻找把 AI 功能织进产品规格的机会。（例子见文末附录。）

**生成者。** 早先 harness 里一次一个功能的做法，对范围管理效果很好。我在这里用了相近的模型，指示生成者以 sprint 工作，一次从规格里拿起一个功能。每个 sprint 用 React、Vite、FastAPI 和 SQLite（后来是 PostgreSQL）这套栈实现应用，并指示生成者在每个 sprint 结束时自我评估，再交给 QA。它也有 git 做版本控制。

**评估者。** 早先 harness 做出的应用常常看起来了不起，真去用时仍有实打实的 bug。为了抓住这些，评估者使用 Playwright MCP，像用户那样点进正在运行的应用，测试 UI 功能、API 端点和数据库状态。然后它按自己找到的 bug，以及一套从实验前端搬过来的标准，给每个 sprint 打分；标准在这里改成覆盖产品深度、功能性、视觉设计和代码质量。每条标准有一个硬阈值，任何一条低于阈值，这个 sprint 就失败，生成者会得到出错之处的详细反馈。

每个 sprint 之前，生成者和评估者谈判一份 sprint 合约：在写任何代码之前，约定这一块工作的「完成」长什么样。这一步存在，是因为产品规格有意停在高层，而我需要一步来弥合用户故事和可测试实现之间的缺口。生成者提出它要做什么、成功如何核验，评估者审这份提议，确认生成者在做对的东西。双方迭代直到达成一致。

沟通通过文件进行：一个 Agent 写一个文件，另一个 Agent 读它，然后要么在这个文件里回应，要么写一个新文件给前一个 Agent 再读。生成者随后按约定的合约构建，再把工作交给 QA。这让工作忠于规格，又不会过早把实现规定死。

#### 跑 harness

这套 harness 的第一版，我用 Claude Opus 4.5，把用户提示同时丢给完整 harness 和一套单 Agent 系统做比较。我用 Opus 4.5，是因为开始这些实验时，它是我们最好的编码模型。

我写了下面这条提示，用来生成一个复古电子游戏制作器：

> 做一个 2D 复古游戏制作器，功能包括关卡编辑器、精灵编辑器、实体行为，以及可玩的测试模式。

下表是 harness 类型、运行时长和总费用。

| Harness | 时长 | 费用 |
| --- | --- | --- |
| 单 Agent | 20 分钟 | 9 美元 |
| 完整 harness | 6 小时 | 200 美元 |

harness 贵了 20 倍以上，但输出质量的差别立刻就看得出来。

我期望的是这样一个界面：我可以搭建一个关卡和它的组成部分（精灵、实体、图块布局），然后按播放，真正去玩这个关卡。我先打开单 Agent 那次运行的输出，最初的应用看起来符合这些预期。

点进去之后，问题开始出现。版面浪费空间，固定高度的面板让视口大部分是空的。工作流很死。想往关卡里放东西时，它提示我先做精灵和实体，但界面里没有任何东西引导我走向这个顺序。更要紧的是，游戏本身是坏的。我的实体出现在屏幕上，但没有任何东西响应输入。钻进代码发现，实体定义和游戏运行时之间的接线断了，表面上看不出断在哪里。

评完单 Agent 那次运行，我把注意力转到 harness 那次运行。这次从同一句提示开始，但规划者那一步把提示展开成一份 16 个功能、分布在十个 sprint 里的规格。它远远超出单 Agent 运行试图做的范围。除了核心编辑器和游玩模式，规格还要求精灵动画系统、行为模板、音效和音乐、AI 辅助的精灵生成器和关卡设计器，以及带可分享链接的游戏导出。我给了规划者我们的前端设计 Skill，它读了这份 Skill，并把它用进规格，为应用建立一套视觉设计语言。对每个 sprint，生成者和评估者谈判一份合约，规定该 sprint 的具体实现细节，以及用来核验完成的可测试行为。

应用立刻比单 Agent 运行更打磨、更顺。画布用满整个视口，面板尺寸合理，界面有一致的视觉身份，顺着规格里的设计方向。单 Agent 运行里我看到的一些笨拙仍然在：工作流仍然没有说清你应当先做精灵和实体，再去填充关卡，我得自己戳一戳才弄明白。这读起来更像是基座模型在产品直觉上的缺口，而不是 harness 被设计来处理的东西，不过它也指出了一个地方：在 harness 内部做有针对性的迭代，可以进一步提高输出质量。

把编辑器走一遍，新运行相对单 Agent 的优势更明显。精灵编辑器更丰富、功能更全，工具调色板更干净，取色器更好，缩放控件更可用。

因为我要求规划者把 AI 功能织进规格，应用还带了一个内置的 Claude 集成，让我可以通过提示生成游戏的不同部分。这显著加快了工作流。

最大的差别在游玩模式。我真的能移动自己的实体、把游戏玩起来。物理还有些毛边——角色跳上平台后和平台重叠，直觉上不对——但核心的东西能工作，这是单 Agent 运行没有做到的。四处移动一会儿之后，我确实碰到了 AI 搭建关卡的一些限制。有一堵大墙我跳不过去，于是卡住了。这说明还有一些常识性的改进和边界情况，harness 可以处理，从而把应用再打磨一层。

读日志可以看清：评估者让实现和规格保持一致。每个 sprint，它走一遍 sprint 合约的测试标准，并通过 Playwright 操练正在运行的应用，对任何偏离预期行为的地方报 bug。合约很细——仅 sprint 3 就有 27 条标准覆盖关卡编辑器——评估者的发现具体到不用额外调查就能动手。下表是评估者指出的几个问题：

| 合约标准 | 评估者的发现 |
| --- | --- |
| 矩形填充工具允许按住拖拽，用所选图块填满一块矩形区域 | 失败。工具只在拖拽的起点和终点放图块，没有填满区域。`fillRectangle` 函数存在，但没有在 mouseUp 时被正确触发。 |
| 用户可以选中并删除已放置的实体出生点 | 失败。`LevelEditor.tsx` 第 892 行的 Delete 键处理要求 `selection` 和 `selectedEntityId` 同时被设置，但点击一个实体只设置了 `selectedEntityId`。条件应当是：已有选区，或者（已选中实体且当前层是 entity）。 |
| 用户可以通过 API 重排动画帧 | 失败。`PUT /frames/reorder` 路由定义在 `/{frame_id}` 路由之后。FastAPI 把 `reorder` 匹配成整数类型的 frame_id，返回 422：“unable to parse string as an integer.” |

把评估者调到这个水平花了功夫。开箱即用时，Claude 是一个糟糕的 QA Agent。早期运行里，我看着它指出合法的问题，然后说服自己这些问题没什么大不了，照样批准工作。它也倾向于测得很浅，不去探边界情况，于是更细的 bug 常常漏过去。调参循环是：读评估者的日志，找出它的判断和我分歧的例子，然后改 QA 的提示去解决这些问题。这个开发循环走了好几轮，评估者的打分方式才让我觉得合理。即便那时，harness 的输出仍显示出模型 QA 能力的限度：小的版面问题、有些地方感觉不直觉的交互，以及评估者没有充分操练到的、嵌得更深的功能里尚未发现的 bug。显然还有更多核验空间，可以靠进一步调参抓住。但和单 Agent 运行相比——那里应用的核心功能干脆不能用——提升是明显的。

#### 迭代 harness

第一批 harness 结果令人鼓舞，但它也臃肿、慢、贵。合乎逻辑的下一步是找到简化 harness、又不让表现下降的办法。这一部分是常识，一部分来自一条更一般的原则：harness 里的每个组件都编码了一条关于「模型自己做不到什么」的假设。这些假设值得做压力测试，既因为它们可能是错的，也因为模型变好时它们会很快过时。我们的博文[《构建高效的 AI Agent》](https://www.anthropic.com/research/building-effective-agents)把底下的想法说成「找到尽可能简单的解法，只在需要时再增加复杂度」，对任何维护 Agent harness 的人，这个模式都会反复出现。

第一次尝试简化时，我把 harness 大幅砍回去，并试了几个有创意的新点子，但没能复现原先的表现。也变得很难说清 harness 设计里哪些部分真正在承重、以什么方式承重。基于那次经验，我改成更有方法的做法：一次去掉一个组件，再看它对最终结果的影响。

就在这些迭代周期进行时，我们还发布了 Opus 4.6，这进一步促使我降低 harness 的复杂度。有充分理由预期 4.6 需要的脚手架会比 4.5 少。引自[发布博文](https://www.anthropic.com/news/claude-opus-4-6)：「［Opus 4.6］规划更仔细，能把智能体式任务维持得更久，能在更大的代码库里更可靠地工作，并有更好的代码审查和调试技能来抓住自己的错误。」它在长上下文检索上的提升也很大。这些都是这套 harness 当初被搭出来去补上的能力。

#### 去掉 sprint 结构

我从整个去掉 sprint 结构开始。sprint 结构曾经帮助把工作拆成块，让模型连贯地做。鉴于 Opus 4.6 的改进，有充分理由相信模型可以原生处理这件事，不再需要这种分解。

规划者和评估者我都留着，因为每一个仍在明显地加价值。没有规划者，生成者会把范围定得过小：面对原始提示，它会不先写规格就开始建，最后做出的应用在功能上不如规划者那一版丰富。

去掉 sprint 结构之后，我把评估者挪到运行结束时的单次检查，而不是每个 sprint 打一次分。模型能干得多了，这改变了评估者在某些运行里的承重程度：它有没有用，取决于任务落在模型自己能可靠做到的范围的哪一侧。在 4.5 上，这条边界很近：我们的构建处在生成者单独能做好的边缘，评估者在整个构建里抓住了有意义的问题。在 4.6 上，模型的原始能力上升，边界往外移。以前需要评估者检查才能被连贯实现的任务，现在常常落在生成者自己就能处理好的范围里；对边界以内的任务，评估者变成不必要的开销。但对构建中仍处在生成者能力边缘的部分，评估者继续提供真实的提升。

实践上的含义是：评估者不是一个固定的要或不要。当任务落在当前模型单独做不到稳定完成的地方时，它的成本才值。

在结构简化之外，我还加了提示，改进 harness 把 AI 功能做进每个应用的方式，具体是让生成者做出一个正经的 Agent，能通过工具驱动应用自己的功能。这需要实打实的迭代，因为相关知识新到 Claude 的训练数据只薄薄盖住一层。但调得够了之后，生成者能正确地把 Agent 做出来。

#### 更新后 harness 的结果

为了检验更新后的 harness，我用下面这条提示生成一个数字音频工作站（DAW），也就是用来作曲、录音和混音的音乐制作程序：

> 用 Web Audio API 在浏览器里做一个功能完整的 DAW。

这次运行仍然又长又贵，大约 4 小时，token 费用 124 美元。

大部分时间花在构建者上。它连贯地跑了两个多小时，不再需要 Opus 4.5 所依赖的 sprint 分解。

| Agent 与阶段 | 时长 | 费用 |
| --- | --- | --- |
| 规划者 | 4.7 分钟 | 0.46 美元 |
| 构建（第 1 轮） | 2 小时 7 分钟 | 71.08 美元 |
| QA（第 1 轮） | 8.8 分钟 | 3.24 美元 |
| 构建（第 2 轮） | 1 小时 2 分钟 | 36.89 美元 |
| QA（第 2 轮） | 6.8 分钟 | 3.09 美元 |
| 构建（第 3 轮） | 10.9 分钟 | 5.88 美元 |
| QA（第 3 轮） | 9.6 分钟 | 4.06 美元 |
| V2 harness 合计 | 3 小时 50 分钟 | 124.70 美元 |

和前一版 harness 一样，规划者把一行提示展开成完整规格。从日志里我能看到，生成者模型把应用和 Agent 的设计规划得不错，把 Agent 接上，并在交给 QA 之前做了测试。

尽管如此，QA Agent 仍然抓住了真实的缺口。它在第一轮反馈里写道：

> 这是一个强的应用，设计保真度出色，AI Agent 扎实，后端也不错。主要失败点是功能完整度——应用看起来令人印象深刻，AI 集成也工作良好，但若干核心 DAW 功能只是展示，没有交互深度：片段不能在时间线上拖动或移动，没有乐器 UI 面板（合成器旋钮、鼓垫），也没有可视化效果器编辑器（EQ 曲线、压缩器表头）。这些不是边界情况——它们是让 DAW 可用的核心交互，而且规格明确要求了它们。

第二轮反馈里，它再次抓住几处功能缺口：

> 仍然存在的缺口：录音仍只是桩（按钮能切换，但没有麦克风采集）；没有实现靠边缘拖拽调整片段大小，也没有片段分割；效果可视化是数字滑杆，不是图形（没有 EQ 曲线）。

生成者在放任自流时仍然容易漏掉细节，或把功能做成桩。QA 在抓住这些最后一公里的问题上仍然有价值，好让生成者去修。

按这条提示，我期望的是这样一个程序：我可以做旋律、和声和鼓点，把它们编成一首歌，并沿途得到一个集成 Agent 的帮助。下面的视频是结果。

[DAW 结果视频](https://cdn.sanity.io/files/4zrzovbb/website/555910f9adb3938734940224e7a6f4c7cbbbd8f2.mp4)

这个应用离专业音乐制作程序还远，Agent 的作曲技能显然还有很多要练。另外，Claude 实际上听不见，这让 QA 反馈环在音乐品味上没那么有效。

但最终的应用具备一个能用的音乐制作程序的全部核心部件：在浏览器里运行的、能工作的编曲视图、调音台和走带控制。除此之外，我完全通过提示拼出了一小段歌曲：Agent 设定速度和调性，铺下旋律，做了鼓轨，调整调音台电平，并加上混响。作曲的核心原语都在，Agent 可以自主驱动它们，用工具从头到尾做出一份简单的成品。你可以说它还没有音准完美——但它正在到那里。

### 接下来

模型继续变好时，大体可以预期它们能工作得更久，也能做更复杂的任务。在一些情况下，这意味着模型周围的脚手架会随时间没那么要紧，开发者可以等下一个模型，看着某些问题自己解开。另一方面，模型越好，就越有空间去开发能完成「超出模型基线所能」的复杂任务的 harness。

带着这一点，这项工作里有几条教训值得带下去。始终值得做的是：拿你正在对着构建的那个模型做实验，在现实问题上读它的记录，并调它的表现去达到你要的结果。做更复杂的任务时，有时还有空间来自把任务分解，并把专门的 Agent 用到问题的每个方面。新模型落地时，通常值得重新检查一套 harness：拆掉对表现不再承重的部分，加上新的部分，去达到以前可能做不到的更强能力。

这项工作让我确信：有意思的 harness 组合所在的空间，并不会因为模型变好而缩小。它是在移动。AI 工程师有意思的工作，是继续找到下一种新的组合。

## 笔记

- 上下文重置和 compaction（上下文压缩）不是同一招：压缩把较早对话摘要进同一段历史，重置是清空窗口，靠交接文件把状态交给下一次会话。Sonnet 4.5 的上下文焦虑强到单靠压缩不够。
- 生成者给自己打分时会偏高。单独的评估者可以调成怀疑的，生成者才有具体批评可以改；评估者仍是 LLM，宽容不会因为「分开」自动消失。
- 同一句复古游戏提示：单 Agent 约 20 分钟、9 美元，完整 harness 约 6 小时、200 美元。贵 20 倍以上，但只有后者把实体接到了能玩的运行时；sprint 3 的合约就有 27 条标准。
- harness 里每个组件都是「模型自己做不到」的假设。Opus 4.6 能连续构建两个多小时之后，sprint 可以拆掉；评估者只在任务仍超出模型单独能稳定完成的范围时才值回成本。DAW 那次约 3 小时 50 分、124.70 美元，QA 仍抓到时间线不能拖、录音只是桩这些缺口。
