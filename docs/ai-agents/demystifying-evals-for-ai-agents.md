# 拆解 AI Agent 评测

**非官方译文。** 官方原文：[Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)（Anthropic · Engineering）。

## 导读

评测在这里被拆成可执行的零件：task（任务）、trial（一次运行）、grader（评分器），以及把它们跑起来的 harness（任务脚手架）。适合已经有 Agent、却只能靠「上线之后感觉变差了」来改的团队。文中先分能力评测和回归评测，再按编码、对话、研究、计算机使用四类 Agent 说明评分器怎么配；后半是从 20–50 条真实失败做到可长期维护的路线。

原文发表于 2026 年 1 月 9 日，作者为 Mikaela Grace、Jeremy Hadfield、Rodrigo Olivares、Jiri De Jonghe。

## 译文

### 引言

好的评测让团队更有把握地把 AI Agent 发出去。没有评测，很容易陷在被动循环里：问题只在生产环境才被抓住，修掉一个失败又引出别的失败。评测让问题和行为变化在影响用户之前就看得见，而且这份价值会随着 Agent 的生命周期累积。

他们在[《构建高效的 AI Agent》](https://www.anthropic.com/engineering/building-effective-agents)里写过：Agent 跨很多轮运行，调用工具、修改状态，并根据中间结果调整。让 AI Agent 有用的那些能力——自主、智能、灵活——也让它们更难评。

通过内部工作，以及和处在 Agent 开发前沿的客户合作，他们学到怎样把 Agent 评测做得更严、也更有用。下面是在真实部署里、跨多种 Agent 架构和用例中真正奏效的做法。

### 评测的结构

一次 evaluation（评测，也常简称 eval）就是对 AI 系统的一次测试：给 AI 一个输入，再对它的输出施加评分逻辑，衡量成功与否。这篇聚焦可以在开发期间跑、不需要真实用户的自动化评测。

单轮评测很直接：一条提示、一份响应、一套评分逻辑。对更早的 LLM，单轮、非智能体式的评测是主要方法。能力往前走之后，多轮评测越来越常见。

![简单评测与多轮评测](https://www-cdn.anthropic.com/images/4zrzovbb/website/bd42e7b2f3e9bb5218142796d3ede4816588dec0-4584x2834.png)

图：简单评测里，Agent 处理一条提示，评分器检查输出是否符合预期。更复杂的多轮评测里，编码 Agent 拿到工具、一项任务（这里是搭建一个 MCP 服务器；MCP 即 Model Context Protocol，模型上下文协议）和一个环境，执行「Agent 循环」（工具调用和推理），并把实现写回环境。评分随后用单元测试确认这个 MCP 服务器能工作。

Agent 评测还要更复杂。Agent 跨很多轮使用工具，一边改环境里的状态，一边适应——错误会传播并叠加。前沿模型还会找出超出静态评测边界的创造性解法。例如 [Opus 4.5](https://www.anthropic.com/news/claude-opus-4-5) 在一道关于订机票的 [τ2-bench](https://github.com/sierra-research/tau2-bench) 题上，发现了政策里的漏洞。按书面标准它「失败」了，但给用户的解法其实更好。

搭建 Agent 评测时，他们使用下面这些定义：

- **task**（任务，也称 problem 或 test case）是一道测试，有明确的输入和成功标准。
- 对一道任务的每次尝试是一次 **trial**（一次运行）。模型输出每次都会变，所以要跑多次 trial，结果才更稳。
- **grader**（评分器）是给 Agent 表现的某一方面打分的逻辑。一道任务可以有多个评分器，每个评分器里可以有多条断言（有时叫 check）。
- **transcript**（记录，也称 trace 或 trajectory）是一次 trial 的完整记录，包括输出、工具调用、推理、中间结果，以及其他交互。对 Anthropic API 来说，这就是评测跑完时的完整 messages 数组：评测期间全部 API 调用和全部返回。
- **outcome**（结果）是 trial 结束时环境里的最终状态。订票 Agent 可能在记录末尾说「您的航班已预订」，但结果是环境的 SQL 数据库里是否真有一条预订。
- **evaluation harness**（评测 harness，任务脚手架）是把评测从头跑到尾的基础设施。它提供指令和工具，并发跑任务，记下每一步，给输出打分，并汇总结果。
- **agent harness**（Agent harness，或称 scaffold）是让模型能够作为 Agent 行动的系统：处理输入、编排工具调用、返回结果。评测「一个 Agent」时，评的是 harness 和模型一起工作。例如 [Claude Code](https://claude.com/product/claude-code) 是一个灵活的 Agent harness，他们用 [Agent SDK](https://platform.claude.com/docs/en/agent-sdk/overview) 里的核心原语搭了[长时运行 Agent harness](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)。
- **evaluation suite**（评测套件）是一组用来测量特定能力或行为的任务。套件里的任务通常共享一个大目标。例如客服评测套件可能测退款、取消和升级处理。

### 为什么要做评测

团队刚开始做 Agent 时，靠手工测试、[内部试用（dogfooding）](https://en.wikipedia.org/wiki/Eating_your_own_dog_food)和直觉，往往能走得比预想远。更严格的评测甚至像是拖慢发布的开销。但过了早期原型阶段，Agent 进了生产并开始放量之后，没有评测的开发就会垮掉。

拐点常常是：用户反馈改完之后 Agent 感觉更差，团队却在「盲飞」，除了猜和试没有别的办法核对。没有评测，调试是被动的：等投诉、手工复现、修 bug，然后希望别处没有退步。团队分不清真退化和噪声，不能在发布前自动用几百个场景测改动，也量不出改进。

他们多次看到这条轨迹。例如 Claude Code 一开始靠 Anthropic 员工和外部用户的反馈快速迭代。后来加上评测：先是简洁度和文件编辑这类窄领域，再是过度工程这类更复杂的行为。这些评测帮助定位问题、引导改进，并让研究和产品的协作有焦点。再加上生产监控、A/B 测试、用户研究等，评测提供信号，让 Claude Code 在放量时还能继续变好。

在 Agent 生命周期的任何阶段，写评测都有用。早期，评测迫使产品团队写清对 Agent 来说什么叫成功；后期，评测帮助守住一条稳定的质量线。

[Descript](https://www.descript.com/) 的 Agent 帮用户剪视频，于是他们围绕成功剪辑工作流的三个维度做评测：别把东西弄坏、做我要求的事、做好。他们从人工评分演进到由产品团队定义标准的 LLM 评分器，并定期做人工校准，现在固定跑两套：一套做质量基准，一套做回归测试。[Bolt](https://bolt.new/) 的 AI 团队动手较晚，当时 Agent 已经用得很广。三个月里，他们搭了一套评测系统：跑 Agent，用静态分析给输出打分，用浏览器 Agent 测应用，并用 LLM 裁判评估遵循指令这类行为。

有的团队在开发一开始就做评测；有的等到规模上来、评测变成改进 Agent 的瓶颈才补。评测在 Agent 开发起步时尤其有用，因为它把期望行为显式编码下来。两个工程师读同一份初始规格，对 AI 该如何处理边界情况可能理解不同。评测套件把这种含糊消掉。无论何时建立，评测都帮助加快开发。

评测也决定你多快能换上新模型。更强的模型出来时，没有评测的团队要测上几周；有评测的竞争对手几天内就能看清模型的强项、调好提示、完成升级。

评测一旦存在，基线和回归测试是顺手得到的：延迟、token 用量、每项任务的成本、错误率，都可以在一组固定任务上跟踪。评测也可以成为产品和研究团队之间带宽最高的沟通渠道，定义研究人员可以去优化的指标。评测的好处显然超出「跟踪退化和改进」。成本先看见、收益后累积，这种复利很容易被漏掉。

### 如何评测 AI Agent

今天大规模部署的 Agent 有几类常见形态，包括编码 Agent、研究 Agent、计算机使用 Agent 和对话 Agent。每一类都可以铺到很多行业，但可以用相近的技术来评。不必从零发明一套评测。下面几节描述几类 Agent 上已经验证过的技术。拿这些方法当底座，再延伸到自己的领域。

#### Agent 的评分器类型

Agent 评测通常组合三类评分器：基于代码的、基于模型的、人工的。每个评分器评的是记录或结果的某一部分。有效评测设计的关键，是为这件事选对评分器。

#### 基于代码的评分器

| 方法 | 优点 | 缺点 |
| --- | --- | --- |
| 字符串匹配（精确、正则、模糊等）；二元测试（fail-to-pass：原先失败的测试变为通过；pass-to-pass：原先通过的测试仍然通过）；静态分析（lint、类型、安全）；结果核验；工具调用核验（用了哪些工具、参数是什么）；记录分析（轮数、token 用量） | 快；便宜；客观；可复现；好调试；能核验具体条件 | 对「合法但和预期模式不完全一致」的变体很脆；缺少细致差别；对一部分更主观的任务能力有限 |

#### 基于模型的评分器

| 方法 | 优点 | 缺点 |
| --- | --- | --- |
| 按量表打分；自然语言断言；成对比较；对照参考的评估；多裁判共识 | 灵活；可扩展；能抓住细微差别；能处理开放式任务；能处理自由形式输出 | 非确定；比代码贵；要和人工评分器校准才准 |

#### 人工评分器

| 方法 | 优点 | 缺点 |
| --- | --- | --- |
| 领域专家复核；众包判断；抽查；A/B 测试；标注者间一致性 | 黄金标准的质量；贴近专家用户的判断；用来校准基于模型的评分器 | 贵；慢；往往需要规模化地用到人类专家 |

对每道任务，计分可以是加权的（多个评分器的分数合起来必须过阈值）、二元的（所有评分器都必须过），或两者混合。

#### 能力评测与回归评测

能力评测，或称「质量」评测，问的是：这个 Agent 什么做得好？它们应当从较低的通过率起步，瞄准 Agent 还吃力的任务，给团队一座要爬的山。

回归评测问的是：Agent 是否还能处理它以前会的全部任务？通过率应当接近 100%。它们防止倒退：分数下降说明有东西坏了，需要修。团队在能力评测上往上爬时，也要跑回归评测，确认改动没有在别处惹麻烦。

Agent 发布并优化之后，通过率已经很高的能力评测可以「毕业」，变成持续运行的回归套件，用来抓住漂移。曾经衡量「我们到底能不能做」的任务，转而衡量「我们是否还能可靠地做」。

#### 评测编码 Agent

编码 Agent 写代码、测代码、调试，像人类开发者一样在代码库里导航、跑命令。对现代编码 Agent，有效评测通常依赖规格清楚的任务、稳定的测试环境，以及对生成代码的充分测试。

确定性评分器对编码 Agent 很自然，因为软件大体上容易评：代码能跑吗，测试过了吗？两个广泛使用的编码 Agent 基准，[SWE-bench Verified](https://www.swebench.com/SWE-bench/) 和 [Terminal-Bench](https://www.tbench.ai/)，走的就是这条路。SWE-bench Verified 给 Agent 流行 Python 仓库里的 GitHub issue，用测试套件给解答打分：只有修好了失败的测试、又没有弄坏已有测试，才算通过。LLM 在这一评测上一年内从 40% 走到 80% 以上。Terminal-Bench 走另一条：它测端到端的技术任务，例如从源码构建 Linux 内核，或训练一个机器学习模型。

一旦有了一组通过/失败测试，用来核验编码任务的关键结果，再给记录打分往往也有用。例如，基于启发式的代码质量规则可以评「生成的代码是否仅仅是测试通过」；带清晰量表的模型评分器可以评 Agent 如何调用工具、如何和用户互动。

**例：编码 Agent 的示意评测**

考虑一道编码任务：Agent 必须修掉一个认证绕过漏洞。如下面这份示意 YAML，可以用评分器和指标一起评这个 Agent。

```yaml
task:
  id: "fix-auth-bypass_1"
  desc: "修复密码字段为空时的认证绕过，以及……"
  graders:
    - type: deterministic_tests
      required: [test_empty_pw_rejected.py, test_null_pw_rejected.py]
    - type: llm_rubric
      rubric: prompts/code_quality.md
    - type: static_analysis
      commands: [ruff, mypy, bandit]
    - type: state_check
      expect:
        security_logs: {event_type: "auth_blocked"}
    - type: tool_calls
      required:
        - {tool: read_file, params: {path: "src/auth/*"}}
        - {tool: edit_file}
        - {tool: run_tests}
  tracked_metrics:
    - type: transcript
      metrics:
        - n_turns
        - n_toolcalls
        - n_total_tokens
    - type: latency
      metrics:
        - time_to_first_token
        - output_tokens_per_sec
        - time_to_last_token
```

这个例子为了说明，把可用评分器的范围都摆了出来。实践里，编码评测通常靠单元测试核验正确性，再用一份 LLM 量表评估整体代码质量，只在需要时再加评分器和指标。

#### 评测对话 Agent

对话 Agent 在客服、销售或辅导等领域和用户互动。和传统聊天机器人不同，它们保持状态、使用工具，并在对话中途采取行动。编码 Agent 和研究 Agent 也可以和用户多轮互动，但对话 Agent 有一个单独的难点：互动本身的质量就是你要评的一部分。有效评测通常依赖可核验的终态结果，以及同时抓住任务完成和互动质量的量表。和多数其他评测不同，它们常常需要第二个 LLM 来模拟用户。他们在[对齐审计 Agent](https://alignment.anthropic.com/2025/automated-auditing/)里用这种方法，通过拉长的、对抗性的对话对模型做压力测试。

对话 Agent 的成功可以是多维的：工单解决了吗（状态检查），是否在 10 轮以内结束（记录约束），语气合适吗（LLM 量表）？把多维性做进去的两个基准是 [τ-Bench](https://arxiv.org/abs/2406.12045) 和它的后继 [τ2-Bench](https://arxiv.org/abs/2506.07982)。它们在零售客服、机票预订等领域模拟多轮互动：一个模型扮演用户人设，Agent 在现实场景里导航。

**例：对话 Agent 的示意评测**

考虑一道客服任务：Agent 必须为一名沮丧的客户办理退款。

```yaml
graders:
  - type: llm_rubric
    rubric: prompts/support_quality.md
    assertions:
      - "Agent 对客户的挫败表现出同理"
      - "解决方案被清楚地解释"
      - "Agent 的回复以 fetch_policy 工具的结果为依据"
  - type: state_check
    expect:
      tickets: {status: resolved}
      refunds: {status: processed}
  - type: tool_calls
    required:
      - {tool: verify_identity}
      - {tool: process_refund, params: {amount: "<=100"}}
      - {tool: send_confirmation}
  - type: transcript
    max_turns: 10
tracked_metrics:
  - type: transcript
    metrics:
      - n_turns
      - n_toolcalls
      - n_total_tokens
  - type: latency
    metrics:
      - time_to_first_token
      - output_tokens_per_sec
      - time_to_last_token
```

和编码 Agent 的例子一样，这道任务为了说明摆出了多种评分器。实践里，对话 Agent 评测通常用基于模型的评分器同时评估沟通质量和目标完成，因为很多任务——例如回答一个问题——可以有多个「正确」解。

#### 评测研究 Agent

研究 Agent 收集、综合、分析信息，然后产出答案或报告这类输出。编码 Agent 有单元测试给出二元的过/不过信号；研究质量只能相对任务来判断。「全面」「来源扎实」甚至「正确」取决于情境：市场扫描、收购尽职调查、科学报告，各自要求不同的标准。

研究评测有独特的困难：专家可能对一份综合是否全面意见不一；参考内容不断变化，地面真相会移动；更长、更开放的输出留下更多出错空间。例如 [BrowseComp](http://arxiv.org/abs/2504.12516) 这类基准测试 AI Agent 能否在开放网页上大海捞针——题目设计成容易核验、难以解出。

搭建研究 Agent 评测的一种策略是组合评分器类型。依据性检查核验主张是否被检索到的来源支持；覆盖检查规定好答案必须包含的关键事实；来源质量检查确认查阅的来源有权威性，而不是仅仅最先被检索到。对有客观正确答案的任务（「X 公司第三季度营收是多少？」），精确匹配就行。LLM 可以标出没有依据的主张和覆盖缺口，也可以核验开放式综合是否连贯、完整。

研究质量主观，因此基于 LLM 的量表要经常对照专家的人工判断做校准，这些 Agent 才能被有效地打分。

#### 计算机使用 Agent

计算机使用 Agent 通过和人相同的界面操作软件——截图、鼠标点击、键盘输入、滚动——而不是通过 API 或代码执行。它们可以使用任何带图形界面（GUI）的应用，从设计工具到遗留的企业软件。评测需要让 Agent 在真实或沙箱环境里跑，在那里使用软件，再检查它是否达成了预期结果。例如 [WebArena](https://arxiv.org/abs/2307.13854) 测基于浏览器的任务，用 URL 和页面状态检查核验 Agent 是否导航正确，并对修改数据的任务做后端状态核验（确认订单真的下了，而不是只出现了确认页）。[OSWorld](https://os-world.github.io/) 把这扩展到完整操作系统控制，任务完成后用评测脚本检查多种产物：文件系统状态、应用配置、数据库内容、UI 元素属性。

浏览器使用 Agent 要在 token 效率和延迟之间取平衡。基于 DOM 的交互执行快，但消耗很多 token；基于截图的交互更慢，但更省 token。例如让 Claude 总结维基百科时，从 DOM 抽出文本更高效。在亚马逊上找一个新的笔记本电脑保护套时，截图更高效（把整个 DOM 抽出来很费 token）。在 Claude for Chrome 这个产品里，他们做了评测，检查 Agent 是否按情境选对工具。这让基于浏览器的任务完成得更快、也更准。

#### 如何看待评测里的非确定性

不论哪一类 Agent，行为都会在不同次运行之间变化，评测结果因此比表面更难解读。每道任务有自己的成功率——也许一道是 90%，另一道是 50%——某次评测跑过的任务，下一次可能失败。有时我们要测的是：对一道任务，Agent 有多经常成功（成功的 trial 占多大比例）。

两个指标帮助抓住这种差别：

[pass@k](https://proceedings.neurips.cc/paper/2019/file/7298332f04ac004a0ca44cc69ecf6f6b-Paper.pdf) 衡量 Agent 在 k 次尝试里至少得到一个正确解的可能性。k 增大，pass@k 上升：更多次「射门」意味着至少成功 1 次的几率更高。pass@1 为 50% 表示模型在评测里有一半任务第一次就成功。编码里，我们往往最关心 Agent 第一次就找到解，也就是 pass@1。另一些场合，提出很多解是可以的，只要其中一个能用。

[pass^k](https://arxiv.org/abs/2406.12045) 衡量全部 k 次 trial 都成功的概率。k 增大，pass^k 下降，因为要求更多次 trial 都一致，是更高的门槛。如果 Agent 单次 trial 成功率是 75%，你跑 3 次，三次全过的概率是 (0.75)³ ≈ 42%。这个指标对面向客户的 Agent 尤其重要：用户期望每一次行为都可靠。

![pass@k 与 pass^k 随 trial 次数分开](https://www-cdn.anthropic.com/images/4zrzovbb/website/3ddac5be07a0773922ec9df06afec55922f8194a-4584x2580.png)

图：pass@k 和 pass^k 随 trial 次数增加而分开。k=1 时两者相同（都等于单次 trial 成功率）。到 k=10，它们讲的是相反的故事：pass@k 趋近 100%，pass^k 落到 0%。

两个指标都有用，用哪个取决于产品要求：一次成功就够的工具用 pass@k；一致性必不可少的 Agent 用 pass^k。

### 从零到一：通向可靠 Agent 评测的路线

这一节是他们在现场验证过的实用建议：从没有评测，到可以信任的评测。可以把它看成评测驱动的 Agent 开发路线：早点定义成功，清楚地测量，持续迭代。

#### 为初始评测集收集任务

**第 0 步：早点开始**

他们看到团队推迟做评测，因为觉得需要几百道任务。实际上，从真实失败里抽出 20–50 道简单任务就是很好的起点。毕竟在 Agent 开发早期，系统的每次改动往往有清楚、明显的影响，效应大，小样本就够。更成熟的 Agent 可能需要更大、更难的评测才能测出更小的效应，但开头最好走 80/20。越晚做，评测越难搭。早期，产品需求自然就能变成测试用例。等太久，你就是在从一套已经在跑的系统上反推成功标准。

**第 1 步：从你已经在手工测的东西开始**

从开发期间就在跑的手工检查开始：每次发布前你核验的行为，以及终端用户常试的任务。如果已经在生产里，看缺陷跟踪和支持队列。把用户报告的失败转成测试用例，套件才会反映真实用法；按用户影响排优先级，力气才花在要紧的地方。

**第 2 步：写出无歧义的任务，并准备参考解**

把任务质量做对，比看起来难。好任务是：两位领域专家独立做，会得出同一个过/不过判决。他们自己能通过这道任务吗？不能的话，任务还要改。任务规格里的含糊会变成指标里的噪声。基于模型的评分器也一样：含糊的量表会给出不一致的判断。

每道任务都应当能被「正确遵循指令」的 Agent 通过。这一点可以很细。例如，审计 Terminal-Bench 时发现：任务让 Agent 写一个脚本，却没有指定文件路径，测试却假定脚本在某个路径上，Agent 可能毫无过错地失败。评分器检查的每一项，都应当能从任务描述里看清楚；Agent 不应当因为规格含糊而失败。对前沿模型，很多次 trial 的通过率都是 0%（也就是 pass@100 为 0%）时，最常见的信号是任务坏了，不是 Agent 无能，应当回头检查任务规格和评分器。对每道任务，做一个参考解很有用：一份已知能通过全部评分器的输出。这证明任务可解，也核验评分器配置正确。

**第 3 步：做平衡的题目集**

既要测「某行为应当发生」的情形，也要测「不应当发生」的情形。单边评测会带来单边优化。例如，如果你只测 Agent 在该搜索时是否搜索，最后可能得到一个几乎什么都去搜的 Agent。尽量避免[类别不平衡](https://developers.google.com/machine-learning/crash-course/overfitting/imbalanced-datasets)的评测。他们在给 [Claude.ai](http://claude.ai) 做网页搜索评测时亲身学到这一点。挑战是：该不搜的时候别让模型去搜，同时又保留它在合适时做大量研究的能力。团队做了两个方向的评测：模型应当搜索的查询（例如查天气），以及应当凭已有知识回答的查询（例如「谁创立了苹果？」）。在触发不足（该搜却不搜）和过度触发（不该搜却去搜）之间找到平衡很难，提示和评测都改了很多轮。更多例题出现时，他们继续往评测里加，以提高覆盖。

#### 设计评测 harness 和评分器

**第 4 步：用稳定环境做一个稳健的评测 harness**

评测里的 Agent 必须和用于生产的 Agent 大体以同样的方式工作，环境本身也不要再引入噪声。每次 trial 应当「隔离」：从干净环境开始。运行之间不必要的共享状态（残留文件、缓存数据、资源耗尽）会让失败彼此相关，原因是基础设施抖动，而不是 Agent 表现。共享状态也会人为抬高性能。例如，在一些内部评测里，他们观察到 Claude 查看先前 trial 的 git 历史，从而在某些任务上获得不公平的优势。如果多次不同的 trial 因为环境里的同一个限制而失败（例如 CPU 内存有限），这些 trial 就不是独立的，因为它们受同一个因素影响，评测结果就不再可靠地衡量 Agent 表现。

**第 5 步：审慎设计评分器**

如上所述，好的评测设计是为 Agent 和任务选择最好的评分器。建议能用确定性评分器就用；需要时或为了额外灵活性再用 LLM 评分器；人工评分器省着用，做额外验证。

一种常见本能是检查 Agent 是否按非常具体的步骤走，例如工具调用的顺序必须正确。他们发现这种做法太死，测试过于脆弱，因为 Agent 经常找到评测设计者没预料到的合法路径。为了不无谓地惩罚创造力，更好的做法往往是评 Agent 产出了什么，而不是它走了哪条路。

对有多个组成部分的任务，做进部分分。一个客服 Agent 正确识别了问题、核验了客户，但没办成退款，仍然明显好过一个立刻失败的。结果里要能表示这条成功的连续谱。

模型评分往往要仔细迭代才能确认准确。以 LLM 为裁判的评分器应当和人类专家紧密校准，才能确信人工评分和模型评分分歧很小。为避免幻觉，给 LLM 一条退路，例如指示它在信息不足时返回 “Unknown”。也可以为任务的每个维度写清楚、结构化的量表，然后用彼此隔离的 LLM 裁判分别给每个维度打分，而不是用一个裁判打所有维度。系统稳了之后，只偶尔做人工复核就够了。

有些评测有隐蔽的失败模式：Agent 表现其实好，分数仍然低，因为评分 bug、Agent harness 的约束或含糊，使 Agent 解不出任务。老练的团队也会漏掉这些。例如 [Opus 4.5 在 CORE-Bench 上起初只有 42%](https://x.com/sayashk/status/1996334941832089732?s=46&t=c5pEvnVdVbMkcR_rcCHplg)，直到一位 Anthropic 研究者发现多处问题：僵硬的评分在期望 “96.124991…” 时惩罚了 “96.12”；任务规格含糊；以及无法精确复现的随机任务。修好 bug、换上约束更少的 scaffold 之后，Opus 4.5 的分数跳到 95%。类似地，[METR 发现](https://x.com/metr_evals/status/2001473506442375645?s=46)他们时间范围基准里有几道配置错误的任务：任务要求 Agent 优化到一个写明的分数阈值，评分却要求超过该阈值。这惩罚了按指令行事的 Claude 这类模型，而忽略写明目标的模型得分更高。仔细复查任务和评分器，可以帮助避开这些问题。

让评分器抗绕过、抗取巧。Agent 不应当能轻易「作弊」通过评测。任务和评分器应当设计成：通过确实意味着解出了问题，而不是利用了无意中留下的漏洞。

#### 长期维护并使用评测

**第 6 步：读记录**

不读很多次 trial 的记录和分数，你不会知道评分器是否工作良好。在 Anthropic，他们投入工具来查看评测记录，并经常花时间去读。任务失败时，记录告诉你是 Agent 真的错了，还是评分器拒绝了一个合法解。它也常常露出 Agent 和评测行为的关键细节。

失败应当显得公平：Agent 错在哪里、为什么，是清楚的。分数不往上走时，我们需要确信原因是 Agent 表现，而不是评测。读记录是你核验「评测量的是真正要紧的东西」的方法，也是 Agent 开发的一项关键技能。

**第 7 步：留意能力评测饱和**

一套 100% 的评测能跟踪回归，但给不出改进信号。评测饱和是指 Agent 通过了所有可解的任务，没有留下改进空间。例如 SWE-bench Verified 的分数今年从 30% 起步，前沿模型现在接近饱和，超过 80%。评测接近饱和时，进展也会变慢，因为只剩下最难的任务。这会让结果具有欺骗性：能力的大幅改进看起来只是分数的小幅上升。例如代码审查创业公司 [Qodo](https://www.qodo.ai/) 起初对 Opus 4.5 无感，因为他们的单次编码评测没有抓住更长、更复杂任务上的增益。作为回应，他们做了一套新的智能体式评测框架，进展的图景清楚得多。

按他们的规矩，在有人钻进评测细节、读过一些记录之前，不按表面分数来理解评测。如果评分不公平、任务含糊、合法解被罚，或 harness 约束了模型，评测就应当改。

**第 8 步：用开放贡献和维护，让评测套件长期健康**

评测套件是活的产物，需要持续关注和清楚的所有权，才会继续有用。

在 Anthropic，他们试过多种维护评测的办法。最有效的是：设专职评测团队拥有核心基础设施，领域专家和产品团队贡献大部分评测任务，并自己跑评测。

对 AI 产品团队，拥有并迭代评测，应当和维护单元测试一样日常。团队可能在「早期测试里能工作」、却达不到未写明预期的 AI 功能上浪费数周；设计良好的评测本可以早点把这些预期露出来。定义评测任务，是检验产品需求是否具体到可以开工的最好办法之一。

他们建议实践评测驱动开发：在 Agent 还做不到之前，就用评测定义计划中的能力，然后迭代到 Agent 表现好。内部他们经常做这样的功能：今天「够好」，但是对几个月后模型能做什么的押注。从低通过率起步的能力评测让这种押注看得见。新模型一落地，跑这套评测很快就能看出哪些押注兑现了。

最接近产品需求和用户的人，最适合定义成功。以当前模型的能力，产品经理、客户成功经理或销售可以用 Claude Code 把一道评测任务做成 PR 贡献上来——让他们做。或者更好：主动给他们条件。

### 评测如何和其他方法一起构成对 Agent 的完整理解

自动化评测可以在几千道任务上对 Agent 跑，不必部署到生产，也不影响真实用户。但这只是理解 Agent 表现的多种方式之一。完整的图景包括生产监控、用户反馈、A/B 测试、手工读记录，以及系统化的人工评估。

### 理解 AI Agent 表现的方法概览

| 方法 | 优点 | 缺点 |
| --- | --- | --- |
| 自动化评测：不用真实用户、用程序跑测试 | 迭代更快；完全可复现；不影响用户；可以在每次提交上跑；不必做生产部署就能大规模测场景 | 前期投入更大；产品和模型演化时要持续维护，以免漂移；如果和真实用法对不上，会制造虚假的信心 |
| 生产监控：跟踪线上系统的指标和错误 | 在规模上揭示真实用户行为；抓住合成评测漏掉的问题；提供 Agent 实际表现的地面真相 | 被动，问题先到用户那里你才知道；信号可能嘈杂；要投入做埋点；缺少用来打分的地面真相 |
| A/B 测试：用真实用户流量比较变体 | 测量真实用户结果（留存、任务完成）；控制混杂因素；可扩展、系统化 | 慢，要数天或数周才显著，且需要足够流量；只测你部署出去的改动；如果不仔细读记录，对指标变化背后的「为什么」信号较少 |
| 用户反馈：踩、缺陷报告这类显式信号 | 露出你没预料到的问题；带着真实用户的真实例子；反馈常常和产品目标相关 | 稀疏且自我选择；偏向严重问题；用户很少解释为什么失败；不是自动的；主要靠用户抓问题会伤害用户 |
| 手工读记录：人读 Agent 对话 | 建立对失败模式的直觉；抓住自动检查漏掉的细微质量问题；帮助校准「好」长什么样，并抓住细节 | 费时；扩不了规模；覆盖不一致；审阅疲劳或不同审阅者会影响信号质量；通常只给定性信号，没有清楚的定量分数 |
| 系统化人工研究：由受过训练的评分者结构化地给 Agent 输出打分 | 多位人工评分者给出黄金标准的质量判断；能处理主观或含糊的任务；为改进基于模型的评分器提供信号 | 相对贵、周转慢；难以频繁跑；评分者之间的分歧需要调和；法律、金融、医疗等复杂领域需要人类专家来做研究 |

这些方法对应 Agent 开发的不同阶段。自动化评测在发布前和 CI/CD 里特别有用：每次 Agent 改动和模型升级都跑，是质量问题的第一道防线。生产监控在发布后接手，检测分布漂移和未预料到的真实失败。有了足够流量之后，A/B 测试用来验证重大改动。用户反馈和读记录是持续的做法，用来补缺口：不断分诊反馈，每周抽记录来读，需要时再深挖。系统化人工研究留给校准 LLM 评分器，或评估以人类共识为参考标准的主观输出。

![多层方法像瑞士奶酪](https://www-cdn.anthropic.com/images/4zrzovbb/website/b77b8dbb7c2e57f063fbc8a087a853d5809b74b0-4584x2580.png)

像安全工程里的[瑞士奶酪模型](https://en.wikipedia.org/wiki/Swiss_cheese_model)：没有单一评测层能抓住每一个问题。多种方法叠在一起，从一层漏过去的失败会被另一层抓住。

最有效的团队把这些方法合在一起：自动化评测用来快速迭代，生产监控提供地面真相，定期人工复核用来校准。

### 结论

没有评测的团队陷在被动循环里：修一个失败，造出另一个，分不清真退化和噪声。早点投入的团队看到的是反面：失败变成测试用例，测试用例防止回归，指标取代猜测，开发因此加速。评测给整个团队一座清楚的山去爬，把「Agent 感觉更差了」变成可以行动的东西。价值会复利，但前提是把评测当成核心部件，而不是事后补上。

模式因 Agent 类型而异，但这里描述的基本点是恒定的。早点开始，不要等完美的套件。从你看到的失败里取出现实任务。定义无歧义、稳健的成功标准。审慎设计评分器，并组合多种类型。确认题目对模型足够难。迭代评测，提高信噪比。去读记录。

AI Agent 评测仍是一个年轻、演变很快的领域。Agent 承担更长的任务、在多 Agent 系统里协作、处理越来越主观的工作时，技术也要跟着改。他们会在学到更多之后继续分享做法。

### 附录：评测框架

若干开源和商业框架可以帮助团队做 Agent 评测，而不必从零搭基础设施。选哪个，取决于 Agent 类型、现有技术栈，以及你需要的是离线评测、生产可观测性，还是两者都要。

[Harbor](https://harborframework.com/) 用来在容器化环境里跑 Agent，具备跨云厂商大规模跑 trial 的基础设施，以及定义任务和评分器的标准格式。Terminal-Bench 2.0 这类流行基准通过 Harbor 注册表分发，因此既容易跑已有基准，也容易跑自定义评测套件。

[Braintrust](https://www.braintrust.dev/) 是一个把离线评测、生产可观测性和实验跟踪合在一起的平台，适合既要在开发中迭代、又要在生产中监控质量的团队。它的 `autoevals` 库包含事实性、相关性等常见维度的预置评分器。

[LangSmith](https://docs.langchain.com/langsmith/evaluation) 提供追踪、离线和在线评测、数据集管理，并与 LangChain 生态紧密集成。[Langfuse](https://langfuse.com/) 提供相近能力，是可自托管的开源替代，适合有数据驻留要求的团队。

[Arize](https://arize.com/) 提供 Phoenix，一个用于 LLM 追踪、调试以及离线或在线评测的开源平台；以及 AX，把 Phoenix 扩展到规模、优化和监控的 SaaS 产品。

很多团队组合多种工具，自己写评测框架，或先用简单的评测脚本起步。他们的看法是：框架可以加速进展、帮助标准化，但框架的好坏取决于你从里面跑过的评测任务。通常最好是尽快选一个贴合工作流的框架，然后把精力投进评测本身：迭代高质量的测试用例和评分器。

## 笔记

- 能力评测要从低通过率起步，给团队一座山；回归评测应接近全过。通过率爬满之后，前者可以毕业成持续运行的回归套件。
- 结果能判定对错时用代码评分器，开放输出用校准过的模型评分器。把工具调用顺序写死，会罚掉模型自己找到的合法路径。
- pass@k 看 k 次里至少成功一次，pass^k 看 k 次全部成功。单次 75%、跑 3 次时，三次全过大约只有 42%。面向用户、要求每次都稳的 Agent 更该看 pass^k。
- 很多次 trial 仍是 0%（例如 pass@100 为 0）时，先怀疑任务或评分器。Opus 4.5 在 CORE-Bench 上从 42% 到 95%，差在僵硬评分和 scaffold，评分期望 “96.124991…” 时罚了 “96.12”。
