# 我们如何构建多 Agent 研究系统

**非官方译文。** 官方原文：[How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)（Anthropic · Engineering）。

## 导读

Claude 的 Research 用编排者–工作者（orchestrator–worker）做开放式检索：主 Agent 拆题，子 Agent 各自开上下文并行搜索，再把最要紧的信息压短交回去。内部研究评测里，Claude Opus 4 当主 Agent、Claude Sonnet 4 当子 Agent，比单用 Opus 4 高出 90.2%；多 Agent 的 token 大约是普通对话的 15 倍。后半是提示词上的原则、怎么评测，以及状态、部署和同步等待在生产里怎么处理。原文发表于 2025 年 6 月 13 日。

## 译文

Claude 现在有 Research 能力，可以在网页、Google Workspace 以及各种集成里搜索，以完成复杂任务。

这套多 Agent 系统从原型走到生产，给他们上了关于系统架构、工具设计和提示词工程的关键一课。多 Agent 系统由多个 Agent 一起工作构成。这里的 Agent，是在循环里自主使用工具的大语言模型。Research 功能里，有一个 Agent 按用户的问题规划研究过程，再用工具造出并行的 Agent，同时去搜信息。多个 Agent 的系统，在协调、评测和可靠性上带来新的难题。

这篇拆开的是对他们管用的原则，希望做自己的多 Agent 系统时用得上。

### 多 Agent 系统的好处

研究工作是开放式问题，需要哪些步骤很难事先预测。复杂题目的探索路径没法写死，过程本身是动态的，而且依赖已经走过的路。人做研究时，会按新发现不断改做法，顺着调查中冒出来的线索走。

这种不可预测，让 AI Agent 特别适合研究任务。研究要求能在调查展开时转弯，或者去看旁边冒出来的关联。模型必须自主跑很多个回合，按中间发现决定往哪个方向追。一条线性的、一次过的流水线处理不了这些任务。

搜索的本质是压缩：从一大片材料里把洞见蒸馏出来。子 Agent 帮助压缩，因为它们并行工作，各自有自己的上下文窗口，同时探问问题的不同侧面，再把最重要的 token 浓缩给领头的研究 Agent。每个子 Agent 也带来关注点分离——不同的工具、提示和探索轨迹——从而减轻路径依赖，让调查可以彻底、独立地进行。

智能一旦过了某个门槛，多 Agent 系统就成了把能力做上去的一条关键路。举个例子：过去十万年里，单个的人变聪明的幅度有限，信息时代的人类社会却因为集体智能和协调能力，能力按指数上升。即便是一般意义上已经很聪明的 Agent，单独行动也有上限；成组的 Agent 能做成的事多得多。

内部评测表明，多 Agent 研究系统尤其擅长广度优先的查询：要同时追多个彼此独立的方向。他们发现，以 Claude Opus 4 为主 Agent、以 Claude Sonnet 4 为子 Agent 的多 Agent 系统，在内部研究评测上比单 Agent 的 Claude Opus 4 高出 90.2%。例如，要找出标普 500 信息技术板块里各家公司的全部董事会成员时，多 Agent 系统把这件事拆成子 Agent 的任务，找到了正确答案；单 Agent 系统用缓慢的顺序搜索，没有找到答案。

多 Agent 系统管用，主要是因为它们帮助把足够多的 token 花在问题上。在他们的分析里，有三个因素解释了 [BrowseComp](https://openai.com/index/browsecomp/) 评测中 95% 的表现方差。BrowseComp 测的是浏览型 Agent 找出难找信息的能力。他们发现，token 用量本身解释了 80% 的方差，另外两个解释因素是工具调用次数和模型选择。这个发现支持他们的架构：把工作分给各自有上下文窗口的 Agent，为并行推理加上更多容量。最新的 Claude 模型是 token 用量上很大的效率乘数：升级到 Claude Sonnet 4 带来的表现提升，大于在 Claude Sonnet 3.7 上把 token 预算翻倍。对超出单个 Agent 上限的任务，多 Agent 架构是在有效地扩大 token 用量。

也有代价：实际用起来，这些架构烧 token 很快。在他们的数据里，Agent 通常大约用掉聊天交互 4 倍的 token，多 Agent 系统大约用掉聊天的 15 倍。要在经济上站得住，多 Agent 系统需要任务本身的价值高到付得起这份增加的表现。另有一些领域，今天也不适合多 Agent：所有 Agent 必须共享同一份上下文，或者 Agent 之间有很多依赖。例如，大多数编码任务里真正能并行的部分比研究少，大语言模型 Agent 也还不太擅长实时地协调、并把工作委托给其他 Agent。他们发现，多 Agent 系统擅长的是这样的高价值任务：并行度很高，信息超过单个上下文窗口，并且要和许多复杂工具打交道。

### Research 的架构概览

Research 系统用的是多 Agent 架构，模式是编排者–工作者：一个主 Agent 协调过程，把工作委托给并行运行的专门子 Agent。

![Advanced Research 的高层架构：Claude.ai 对话接到多 Agent 研究系统](https://www-cdn.anthropic.com/images/4zrzovbb/website/1198befc0b33726c45692ac40f764022f4de1bf2-4584x2579.png)

图：多 Agent 架构在运转。用户查询流过一个主 Agent，主 Agent 造出专门的子 Agent，并行搜索不同侧面。

图的标题是「High-level Architecture of Advanced Research」。左侧是 Claude.ai 对话，示例问题大意是：2025 年在美国做 AI Agent 的公司有哪些，列出至少 100 家；每家写上名称、网站、产品、在做什么、构建的 Agent 类型，以及所在垂直领域或行业。「User request」把问题送进右侧的多 Agent 研究系统，「Final report」把最终报告送回对话。右侧中央是 Lead agent（orchestrator）。它的工具写成：search tools + MCP tools + memory + `run_subagent` + `complete_task`。旁边连着 Citations subagent 和 Memory，下面连着三个 Search subagent，每个搜索子 Agent 自己还有一条回路。

用户提交查询后，主 Agent 分析问题、制定策略，并生出子 Agent，同时探索不同侧面。如上图所示，子 Agent 充当智能过滤器：反复使用搜索工具收集信息——这个例子里是 2025 年的 AI Agent 公司——然后把一份公司名单交回主 Agent，由主 Agent 汇编成最终答案。

传统的检索增强生成（Retrieval Augmented Generation，RAG）用的是静态检索：取出与输入查询最相似的一批文本块，再用这些块生成回复。他们的架构用的是多步搜索：动态地找到相关信息，适应新的发现，并分析结果，以形成高质量的答案。

![多 Agent 系统的过程图：从用户查询到带引用的研究报告](https://www-cdn.anthropic.com/images/4zrzovbb/website/3bde53c9578d74f6e05c3e515e20b910c5a8c20a-4584x4584.png)

图注如下。这张过程图展示多 Agent Research 系统的完整工作流。用户提交查询后，系统创建一个 LeadResearcher Agent，进入迭代的研究过程。LeadResearcher 先想清做法，并把计划存进 Memory，以便把上下文留住：上下文窗口一旦超过 200,000 个 token 就会被截断，把计划留下来很重要。然后它创建专门的子 Agent（图中画了两个，数量可以是任意的），各自带着具体的研究任务。每个子 Agent 独立做网页搜索，用交错思考（[interleaved thinking](https://docs.anthropic.com/en/docs/build-with-claude/extended-thinking#interleaved-thinking)）评估工具结果，再把发现交回 LeadResearcher。LeadResearcher 综合这些结果，决定还要不要继续研究——如果要，它可以再创建子 Agent，或调整策略。信息足够之后，系统退出研究循环，把全部发现交给一个 CitationAgent。CitationAgent 处理文档和研究报告，标出引用应落在的具体位置。这样，所有论断都正确地归到来源上。带引用的最终研究结果再返回给用户。

图中的泳道从左到右是 User、System、LeadResearcher、Subagent1、Subagent2、Memory、CitationAgent。循环里能看见的步骤包括 `think`（计划做法、评估结果、综合结果）、把计划存进记忆、取回上下文、为侧面 A 和侧面 B 创建子 Agent、`web_search`、`complete_task`。接着判断还要不要继续研究：退出循环，或继续循环。退出后，System 收到带研究结果的 `complete_task`，CitationAgent 处理文档和研究报告以标出引用位置，再交回已经插入引用的报告。System 把结果持久化，最后把带引用的研究结果返回用户。

### 研究 Agent 的提示词工程与评测

多 Agent 系统和单 Agent 系统有关键差别，其中之一是协调复杂度涨得很快。早期的 Agent 会犯这样的错：为简单查询生出 50 个子 Agent，为并不存在的来源在网上无休止地翻，以及用过多的进度更新互相打扰。每个 Agent 都由提示词驾驭，所以提示词工程是他们改善这些行为的主要杠杆。下面是为 Agent 写提示时学到的一些原则：

1. **像你的 Agent 那样去想。** 要迭代提示，得理解它的效果。为此，他们用 [Console](https://console.anthropic.com/) 做模拟，放上系统里原样的提示和工具，再一步步看 Agent 工作。失败模式立刻露出来：已经有足够结果还继续，搜索查询写得过于冗长，或者选错工具。有效的提示依赖于对 Agent 形成准确的心智模型，这样最有影响的改动会变得明显。
2. **教会编排者如何委托。** 在他们的系统里，主 Agent 把查询拆成子任务，再向子 Agent 描述这些子任务。每个子 Agent 需要：一个目标、一种输出格式、关于该用哪些工具和来源的指导，以及清楚的任务边界。任务描述不够细时，Agent 会重复劳动、留下空隙，或者找不到必要的信息。一开始他们让主 Agent 给出简单、很短的指示，比如「研究半导体短缺」，结果这些指示常常含糊到让子 Agent 误解任务，或者和其他 Agent 做完全相同的搜索。例如，一个子 Agent 去查 2021 年的汽车芯片危机，另外两个却在重复调查 2025 年当下的供应链，没有形成有效的分工。
3. **让投入跟上查询的复杂度。** Agent 很难判断不同任务该花多少力气，所以他们把伸缩规则写进提示。简单的事实查找只要 1 个 Agent、3 到 10 次工具调用；直接的比较可能需要 2 到 4 个子 Agent，每个 10 到 15 次调用；复杂研究可能用到 10 个以上的子 Agent，职责划分清楚。这些明确的指引帮助主 Agent 有效分配资源，并避免在简单查询上投入过度——这是早期版本里常见的失败模式。
4. **工具的设计和选择至关重要。** Agent 与工具的界面，和人机界面一样关键。用对工具才有效率——往往还是严格必要的。例如，一个 Agent 去网上搜一段只存在于 Slack 里的上下文，从一开始就没希望。给模型接上外部工具的 [MCP 服务器](https://modelcontextprotocol.io/introduction) 会让这个问题叠加：Agent 会遇到从没见过的工具，描述质量又参差不齐。他们给 Agent 明确的启发规则，例如：先查看全部可用工具，让工具用法匹配用户意图，广泛的外部探索用网页搜索，或者优先用专门工具而不是通用工具。糟糕的工具描述会把 Agent 整个带上错误的路，所以每个工具都要有彼此不同的用途和清楚的描述。
5. **让 Agent 改进自己。** 他们发现 Claude 4 模型可以是很好的提示词工程师。给它一条提示和一个失败模式，它能诊断 Agent 为什么失败，并提出改进。他们甚至做了一个工具测试 Agent：给它一个有缺陷的 MCP 工具，它会试着用这个工具，然后改写工具描述，以避免失败。把工具测上几十次之后，这个 Agent 找出了关键的细微之处和 bug。改善工具顺手程度的这个过程，让以后使用新描述的 Agent 把任务完成时间缩短了 40%，因为它们避开了大多数错误。
6. **先宽后窄。** 搜索策略应该像熟练的人类研究者：先看全貌，再钻进细节。Agent 常常默认写出又长又具体的查询，返回的结果很少。他们用提示抵消这种倾向：让 Agent 从短而宽的查询开始，评估有什么可看，再逐步收窄焦点。
7. **引导思考过程。** [扩展思考模式](https://docs.anthropic.com/en/docs/build-with-claude/extended-thinking)会让 Claude 在可见的思考过程里多输出一些 token，可以当作一块可控的草稿纸。主 Agent 用思考来计划做法：评估哪些工具适合这个任务，判断查询复杂度和子 Agent 数量，并规定每个子 Agent 的角色。他们的测试表明，扩展思考改善了指令遵循、推理和效率。子 Agent 也会先计划，然后在工具结果之后使用[交错思考](https://docs.anthropic.com/en/docs/build-with-claude/extended-thinking#interleaved-thinking)，以评估质量、找出空隙、改进下一次查询。这让子 Agent 更能适应任何任务。
8. **并行工具调用改变速度和表现。** 复杂的研究任务自然要探许多来源。早期的 Agent 做顺序搜索，慢得难受。为了速度，他们引入两种并行：（1）主 Agent 并行拉起 3 到 5 个子 Agent，而不是串行；（2）子 Agent 并行使用 3 个以上的工具。这些改动把复杂查询的研究时间最多砍掉 90%，让 Research 在几分钟而不是几小时里做更多工作，同时比其他系统覆盖更多信息。

他们的提示策略着重灌输好的启发，而不是刚性规则。他们研究了熟练的人怎样做研究任务，并把这些策略编码进提示——例如把难题拆成更小的任务，仔细评估来源质量，按新信息调整搜索方法，以及辨认何时该追求深度（把一个题目查透）或广度（并行探索许多题目）。他们也主动减轻意料之外的副作用：设置明确的护栏，防止 Agent 螺旋式失控。最后，他们把迭代环做快，配上可观测性和测试用例。

### 怎样有效评测 Agent

好的评测对做可靠的 AI 应用必不可少，Agent 也一样。评测多 Agent 系统却有独特的难题。传统评测常常假定 AI 每次走同样的步骤：给定输入 X，系统应沿路径 Y 产出输出 Z。多 Agent 系统不是这样工作的。即使起点完全相同，Agent 也可能走完全不同、但都成立的路径到达目标。一个 Agent 可能搜三个来源，另一个搜十个，或者用不同的工具找到同一个答案。因为并不总知道正确步骤是什么，通常也不能只检查 Agent 有没有遵循事先规定的「正确」步骤。需要的是灵活的评测方法：判断 Agent 是否达成了正确的结果，同时也遵循了合理的过程。

**马上用小样本开始评测。** 在 Agent 开发的早期，改动的影响往往很大，因为容易拿到的改进很多。改一改提示，成功率就可能从 30% 升到 80%。效应这么大时，几个测试用例就能看出变化。他们从大约 20 条代表真实用法的查询开始。测这些查询，常常就能把改动的影响看得很清楚。他们常听到 AI 开发团队推迟建立评测，因为相信只有包含成百个测试用例的大评测才有用。更好的做法是立刻开始小规模测试，用几个例子就行，而不是一直等到能做出更彻底的评测。

**做得好时，用 LLM 当评审可以扩展。** 研究产出很难用程序来评：它们是自由文本，也很少有唯一正确答案。用大语言模型给产出打分是自然的选择。他们用一个 LLM 评审，按一套量规里的标准评估每一份产出：事实准确性（论断与来源相符吗？）、引用准确性（引用的来源与论断相符吗？）、完整性（要求的各个方面都覆盖了吗？）、来源质量（用的是一手来源，还是质量较低的二手来源？）、工具效率（用对了工具，而且次数合理吗？）。他们试过用多个评审分别评估每个方面，结果发现最一致、也最贴近人类判断的，是一次 LLM 调用、一条提示，输出 0.0 到 1.0 的分数，外加一个通过或失败的等级。当评测用例确实有明确答案时，这个方法尤其有效，可以用 LLM 评审简单核对答案对不对（例如：它是否准确列出了研发预算最高的前 3 家制药公司？）。用 LLM 当评审，让他们能成规模地评估成百份产出。

**人工评测抓住自动化漏掉的东西。** 人去测 Agent，会找到评测漏掉的边界情况。包括不寻常查询上的幻觉答案、系统故障，或者细微的来源选择偏差。在他们的情况里，人工测试者注意到，早期的 Agent 一贯选择经过 SEO 优化的内容农场，而不是学术 PDF 或个人博客这类权威、但排名没那么靠前的来源。在提示里加上来源质量的启发规则，帮助解决了这个问题。即便处在自动化评测的世界里，手工测试仍然必不可少。

多 Agent 系统有涌现行为：没有专门编程也会出现。例如，对主 Agent 的小改动，会不可预测地改变子 Agent 的行为。成功需要理解交互模式，而不只是单个 Agent 的行为。因此，给这些 Agent 的最好提示不只是严格的指令，而是协作的框架：规定分工、解题方法和力气预算。要把这一点做对，靠的是仔细的提示和工具设计、扎实的启发、可观测性，以及很紧的反馈环。系统里的示例提示，见 Cookbook 中的[开源提示](https://platform.claude.com/cookbook/patterns-agents-basic-workflows)。

### 生产可靠性与工程难题

在传统软件里，一个 bug 可能弄坏一个功能、拖累性能，或者造成宕机。在 Agent 式系统里，小小的改动会级联成很大的行为变化。这使为一类必须在长时间运行的过程里维持状态的复杂 Agent 写代码，变得格外困难。

**Agent 有状态，错误会复合。** Agent 可以跑很长时间，跨许多次工具调用维持状态。这意味着代码要能持久地执行，并沿途处理错误。没有有效的缓解时，小小的系统故障对 Agent 可以是灾难性的。出错之后不能从头再来：重跑又贵，也让用户沮丧。他们做的是能从错误发生时 Agent 所在的位置接着跑的系统。他们也用模型的智能把问题处理得体面：例如，告诉 Agent 某个工具正在失败，让它自己适应，效果好得令人意外。他们把建在 Claude 上的 AI Agent 的适应性，和确定性的保障结合在一起，比如重试逻辑和定期检查点。

**调试受益于新的做法。** Agent 做动态决策，即使提示相同，各次运行之间也不确定。这让调试更难。例如，用户会报告 Agent「找不到明显的信息」，他们却看不出为什么。是搜索查询写得差？来源选得差？还是碰上了工具失败？加上完整的生产追踪之后，他们才能诊断 Agent 为什么失败，并系统地修问题。在标准的可观测性之外，他们监控 Agent 的决策模式和交互结构——全程不监控单次对话的内容，以保持用户隐私。这种高层的可观测性帮助他们诊断根因、发现意料之外的行为，并修掉常见故障。

**部署需要仔细协调。** Agent 系统是提示、工具和执行逻辑织成的、高度有状态的网，几乎不间断地跑。这意味着每次部署更新时，Agent 可能正处在过程中的任何位置。因此要防止本来出于好意的代码改动弄坏正在跑的 Agent。不能让每个 Agent 在同一时刻切到新版本。他们用[彩虹部署](https://brandon.dimcheff.com/2018/02/rainbow-deploys-with-kubernetes/)避免打扰正在运行的 Agent：新旧版本同时保持运行，把流量从旧版本逐渐移到新版本。

**同步执行造成瓶颈。** 目前，主 Agent 同步执行子 Agent，等每一组子 Agent 完成再继续。这简化了协调，却在 Agent 之间的信息流上造成瓶颈。例如，主 Agent 不能在中途引导子 Agent，子 Agent 之间不能协调，整个系统还可能因为等一个子 Agent 搜完而被堵住。异步执行会带来额外的并行：Agent 同时工作，并在需要时创建新的子 Agent。但这种异步也在结果协调、状态一致性和错误在子 Agent 之间的传播上增加了难题。随着模型能处理更长、更复杂的研究任务，他们预期性能上的收益会让这份复杂度值得。

### 结论

构建 AI Agent 时，最后一英里常常变成旅程的大部分。在开发者机器上能跑的代码库，要变成可靠的生产系统，需要大量工程。Agent 式系统里错误的复合性质，意味着对传统软件只是小问题的事，可以把 Agent 整个带离轨道。一步失败，就可能让 Agent 走上完全不同的轨迹，导致不可预测的结果。由于这篇里写到的种种原因，原型和生产之间的差距，常常比预料的更宽。

尽管有这些难题，多 Agent 系统已经证明对开放式研究任务有价值。用户说，Claude 帮他们找到原先没想到的商业机会，在复杂的医疗选项里找出路，解决棘手的技术 bug，并通过揭开他们独自不会发现的研究关联，省下多达数天的工作。多 Agent 研究系统可以在规模上可靠运转，靠的是仔细的工程、全面的测试、注重细节的提示和工具设计、稳健的运维实践，以及研究、产品和工程团队之间紧密的协作——这些人对当前 Agent 的能力有清楚的理解。他们已经看到，这些系统在改变人们解决复杂问题的方式。

### 附录

下面是关于多 Agent 系统的一些补充、零散的提示。

**对会在许多回合里改写状态的 Agent，做终态评测。** 评测那些在多轮对话中修改持久状态的 Agent，有独特的难题。和只读的研究任务不同，每一个动作都会改变后续步骤所处的环境，造成传统评测方法难以处理的依赖。他们发现，把重点放在终态评测上，而不是逐回合分析，是成功的。不要判断 Agent 有没有遵循某个特定过程，要评估它是否达到了正确的最终状态。这种做法承认 Agent 可能找到通向同一目标的其他路径，同时仍然确保它们交付预期的结果。对复杂工作流，把评测拆成离散的检查点——某些状态变化应当已经发生的地方——而不是试图校验每一个中间步骤。

**长时程对话管理。** 生产中的 Agent 常常进行跨越数百个回合的对话，需要仔细的上下文管理策略。对话一拉长，标准的上下文窗口就不够用，必须有智能的压缩和记忆机制。他们实现的模式是：Agent 把已经完成的工作阶段做成摘要，把必要信息存进外部记忆，再进入新任务。上下文快到上限时，Agent 可以生出上下文干净的新子 Agent，并通过仔细的交接保持连续性。它们还可以从记忆里取回已存的上下文，比如研究计划，而不是一到上下文上限就把先前的工作丢掉。这种分布式做法避免上下文溢出，同时在很长的交互里保持对话连贯。

**把子 Agent 的输出写到文件系统，把「传话游戏」减到最小。** 对某些类型的结果，子 Agent 的输出可以直接绕过主编排者，保真度和性能都会更好。不必要求子 Agent 把一切都通过主 Agent 转述，可以实现一套产物系统，让专门的 Agent 创建独立持久的输出。子 Agent 调用工具，把工作存进外部系统，再把很轻的引用交回协调者。这避免多阶段处理中的信息损失，也减少把大块输出抄进对话历史所带来的 token 开销。这个模式对结构化输出尤其合适，比如代码、报告或数据可视化：子 Agent 的专门提示产出的结果，好过先滤过一个通用协调者。
