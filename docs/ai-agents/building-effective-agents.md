# 构建高效的 AI Agent

**非官方译文。** 官方原文：[Building Effective AI Agents](https://www.anthropic.com/engineering/building-effective-agents)（Anthropic · Engineering）。

## 导读

这篇把「带工具的模型系统」拆成两类：步骤事先写死的工作流，以及由模型自己决定下一步的 Agent。适合刚开始做 Agent、又怕一上来就上复杂框架的人。文里的几种工作流和三条原则，是后面上下文工程、工具、评测和多 Agent 的共同语言。

原文发表于 2024 年 12 月 19 日。页首有一条更新：文中描述的工具生态此后变化很大，Anthropic 当前做法见他们如何构建 Claude Managed Agents，以及 Managed Agents 文档。

## 译文

过去一年，Anthropic 和各行业几十个团队一起做大语言模型（LLM）Agent。做得好的实现，通常并不依赖复杂框架或专用库，而是用简单、可组合的模式搭出来。

这篇分享他们和客户一起做、以及自己做 Agent 时的经验，给开发者一些实际建议。

### 什么是 Agent

「Agent」可以有好几种定义。有的客户把它理解成能长时间独立运行、用各种工具完成复杂任务的全自主系统。也有人用它指更规定性的实现：按预先写好的工作流走。Anthropic 把这些变体都归为 agentic systems（智能体式系统），但在架构上把工作流和 Agent 分开：

- 工作流是用预先写好的代码路径，把 LLM 和工具编排起来的系统。
- Agent 则是由 LLM 动态指挥自己的过程和工具使用、并保持对「任务怎么完成」的控制的系统。

下文会分别展开。附录 1（「实践中的 Agent」）写了客户觉得特别有价值的两个领域。

### 何时用、何时不用

用 LLM 做应用时，建议先找最简单的解法，只在必要时再加复杂度。这可能意味着根本不做智能体式系统。这类系统常常用延迟和成本换更好的任务表现，要先想清楚这笔交换值不值。

复杂度确实有必要时：任务边界清楚，工作流更能给出可预期、一致的结果；需要灵活、并且要在规模上由模型做决策时，Agent 更合适。对很多应用来说，把单次 LLM 调用加上检索和上下文示例优化好，通常就够了。

### 何时以及如何使用框架

不少框架让智能体式系统更好上手，包括：

- Claude Agent SDK
- AWS 的 Strands Agents SDK
- Rivet：拖拽式 GUI，用来搭 LLM 工作流
- Vellum：另一套用来构建和测试复杂工作流的 GUI 工具

这些框架把调用 LLM、定义和解析工具、把多次调用串起来这类底层工作简化了，起步很快。但它们也常常多加一层抽象，把底下的提示和响应遮住，更难调试。它们还会让人忍不住加复杂度，而更简单的做法其实够用。

建议开发者先直接用 LLM API：很多模式几行代码就能实现。如果用框架，要弄懂底下的代码。对「引擎盖下面是什么」的错误假设，是客户出错的常见来源。

示例实现可以看他们的 cookbook。

### 构件、工作流与 Agent

这一节写他们在生产里见过的常见模式。从基础构件「增强后的 LLM」开始，再逐步加复杂度：从简单的组合式工作流，到自主 Agent。

#### 构件：增强后的 LLM

智能体式系统的基本构件，是加上检索、工具和记忆等增强的 LLM。当前模型可以主动使用这些能力：自己生成搜索查询、选择合适的工具、决定保留哪些信息。

图：增强后的 LLM。原文示意图表示模型在检索、工具和记忆的加持下工作。图见[原文](https://www.anthropic.com/engineering/building-effective-agents)。

实现上建议抓住两点：按具体用例裁剪这些能力，并给 LLM 一个容易用、文档清楚的接口。实现方式很多，其中之一是当时新发布的 MCP（Model Context Protocol，模型上下文协议）：开发者用一个简单的客户端，就能接上不断增长的第三方工具生态。

后文默认每次 LLM 调用都能用到这些增强能力。

#### 工作流：提示链

提示链把任务拆成一串步骤，每一次 LLM 调用处理上一次的输出。可以在中间步骤加上程序化检查（原文图中的「gate」，门），确认流程还在正轨上。

图：提示链工作流。若干 LLM 调用按顺序相连，中间可以有门。图见[原文](https://www.anthropic.com/engineering/building-effective-agents)。

何时使用：任务可以干净地拆成固定子任务时很合适。主要目的是用延迟换更高的准确度，让每一次 LLM 调用都变成更容易的任务。

适用例子：

- 先生成营销文案，再翻译成另一种语言。
- 先写文档大纲，检查大纲是否满足某些标准，再按大纲写正文。

#### 工作流：路由

路由对输入分类，再把它送到专门的后续任务。这样可以分离关注点，并写出更专门的提示。没有这一步时，为某一种输入做的优化，往往会伤害其他输入上的表现。

图：路由工作流。一次分类把输入分到不同的后续处理。图见[原文](https://www.anthropic.com/engineering/building-effective-agents)。

何时使用：复杂任务里存在适合分开处理的清晰类别，而且分类本身可以做准——无论是用 LLM，还是用更传统的分类模型或算法。

适用例子：

- 把不同类型的客服问题（一般咨询、退款、技术支持）送进不同的下游流程、提示和工具。
- 把简单、常见的问题路由到更小、更省的模型（如 Claude Haiku 4.5），把难的、不常见的问题路由到能力更强的模型（如 Claude Sonnet 4.5），以换取整体最好的表现。

#### 工作流：并行化

LLM 有时可以同时做一件任务的不同部分，再由程序把输出汇总。并行化有两种主要变体：

- 分段（sectioning）：把任务拆成彼此独立的子任务，并行跑。
- 投票（voting）：同一任务跑多次，得到多样的输出。

图：并行化工作流。多个 LLM 调用同时进行，结果再汇总。图见[原文](https://www.anthropic.com/engineering/building-effective-agents)。

何时使用：拆开的子任务可以并行以换速度，或者需要多种视角、多次尝试来提高把握时，并行化有效。对有多方面考量的复杂任务，把每一方面交给单独的 LLM 调用，通常比一次调用兼顾所有方面更好，因为注意力可以集中。

适用例子：

分段：

- 做护栏：一个模型实例处理用户查询，另一个筛查不当内容或请求。这往往比同一次 LLM 调用既做护栏又写正文更好。
- 自动化评测：每一次 LLM 调用评估模型在给定提示上的不同方面。

投票：

- 审查一段代码的漏洞：若干不同提示分别审阅，发现问题就标出来。
- 判断某段内容是否不当：多个提示评估不同方面，或要求不同的投票阈值，以平衡误报和漏报。

#### 工作流：编排者–工作者

在编排者–工作者（orchestrator-workers）工作流里，一个中心 LLM 动态拆任务，分给工作者 LLM，再综合它们的结果。

图：编排者–工作者工作流。编排者决定子任务，工作者执行，编排者再汇总。图见[原文](https://www.anthropic.com/engineering/building-effective-agents)。

何时使用：适合无法事先预测需要哪些子任务的复杂任务。以写代码为例，要改哪些文件、每个文件改什么，往往取决于具体任务。它和并行化在拓扑上相似，关键差别是灵活性：子任务不是预先定义的，而是编排者根据具体输入决定的。

适用例子：

- 每次都要对多个文件做复杂修改的编码产品。
- 需要从多个来源收集并分析信息、寻找可能相关内容的搜索任务。

#### 工作流：评估者–优化者

在评估者–优化者工作流里，一次 LLM 调用生成回复，另一次在循环里给出评估和反馈。

图：评估者–优化者工作流。生成与评估交替，直到达到标准。图见[原文](https://www.anthropic.com/engineering/building-effective-agents)。

何时使用：评估标准清楚、而且迭代打磨能带来可衡量的收益时特别有效。两个拟合信号：其一，人把反馈说清楚之后，LLM 的回复确实能变好；其二，LLM 自己也能给出这种反馈。这类似于人写文章时反复修改、直到成稿的过程。

适用例子：

- 文学翻译：译者 LLM 一开始抓不住的细微差别，评估者 LLM 可以提出有用的批评。
- 复杂搜索：需要多轮搜索和分析才能收集全面信息，由评估者决定是否还要再搜。

#### Agent

随着 LLM 在几项关键能力上成熟——理解复杂输入、进行推理和规划、可靠地使用工具、从错误中恢复——Agent 开始出现在生产里。Agent 从人的一条指令或一轮交互式讨论开始。任务清楚之后，它们独立计划和运行，必要时再回到人那里要更多信息或判断。执行过程中，每一步都要从环境拿到「地面真值」（例如工具调用结果或代码执行结果），用来判断进展。可以在检查点或遇到阻碍时停下来等人的反馈。任务常常在完成时结束，也常见加上停止条件（例如最大迭代次数）以保持控制。

Agent 能处理复杂任务，但实现往往直接：通常就是 LLM 在循环里根据环境反馈使用工具。因此，把工具集和文档设计清楚、想清楚，至关重要。工具开发的做法在附录 2（「为工具做提示词工程」）里展开。

图：自主 Agent。人给出任务后，模型在循环中规划、调用工具、读取环境反馈。图见[原文](https://www.anthropic.com/engineering/building-effective-agents)。

何时使用 Agent：问题是开放的，很难或无法预测需要多少步，也不能把路径写死。LLM 可能会跑很多轮，你必须对它的决策有一定信任。自主性使 Agent 适合在受信任的环境里把任务做大。

自主也意味着更高的成本，以及错误会复合。建议在沙箱里做充分测试，并加上合适的护栏。

他们自己的实现里，Agent 有用的例子：

- 一个编码 Agent，用来解决 SWE-bench 任务：根据任务描述修改许多文件。
- 「computer use」参考实现：Claude 使用计算机来完成任务。

图：编码 Agent 的高层流程。图见[原文](https://www.anthropic.com/engineering/building-effective-agents)。

### 组合与定制这些模式

这些构件不是规定。它们是开发者可以按用例塑造、组合的常见模式。和任何 LLM 功能一样，成功的关键是测量表现并迭代实现。再说一次：只有在复杂度能明显改善结果时，才考虑加上它。

### 小结

在 LLM 领域成功，不是做出最复杂的系统，而是做出适合你需要的系统。从简单提示开始，用全面的评估去优化，只有更简单的办法不够时，才加上多步的智能体式系统。

实现 Agent 时，他们尽量遵循三条原则：

1. 保持 Agent 设计简单。
2. 把规划步骤显式展示出来，优先考虑透明。
3. 通过充分的工具文档和测试，仔细打造 Agent–计算机接口（ACI）。

框架能帮你快速起步，但进入生产时，不要犹豫减少抽象层，用基本组件来搭建。遵循这些原则，做出的 Agent 不仅强，而且可靠、可维护，并被使用者信任。

### 附录 1：实践中的 Agent

和客户的合作里，有两类 AI Agent 应用特别有希望，能说明上面这些模式的实际价值。两者都说明：Agent 在同时需要对话和行动、成功标准清楚、能形成反馈循环、并且有有意义的人工监督的任务上，增值最大。

#### A. 客户支持

客户支持把熟悉的聊天界面，和通过工具集成增强的能力结合在一起。它天然适合更开放的 Agent，因为：

- 支持交互自然地沿着对话进行，同时又需要外部信息和动作；
- 可以集成工具，拉取客户数据、订单历史和知识库文章；
- 退款、更新工单等动作可以程序化处理；
- 成功可以用用户定义的「解决」来清楚衡量。

若干公司用按成功解决计费的定价，证明了这条路可行，也表明他们对 Agent 的效果有信心。

#### B. 编码 Agent

软件开发显示出 LLM 功能的显著潜力：能力从代码补全演进到自主解决问题。Agent 在这里特别有效，因为：

- 代码方案可以用自动化测试验证；
- Agent 可以用测试结果作为反馈来迭代；
- 问题空间定义清楚、结构良好；
- 输出质量可以客观衡量。

在他们自己的实现里，Agent 已经可以仅根据 pull request 描述，在 SWE-bench Verified 基准上解决真实的 GitHub issue。不过，自动化测试能帮忙验证功能，人工审查对「方案是否符合更广的系统要求」仍然关键。

### 附录 2：为工具做提示词工程

无论你在建哪种智能体式系统，工具多半都是 Agent 的重要部分。工具让 Claude 与外部服务和 API 交互：在 API 里写明它们的确切结构和定义。Claude 回复时，如果打算调用工具，会在 API 响应里带上一个工具使用块。工具定义和规格应得的提示词工程注意力，不亚于整体提示。这个简短附录说明如何为工具做提示词工程。

同一个动作往往有几种写法。例如，改文件可以写 diff，也可以重写整个文件。结构化输出可以把代码放在 Markdown 里，也可以放在 JSON 里。在软件工程里，这类差别是表面的，可以无损互转。但对 LLM 来说，有些格式比另一些难写得多。写 diff 要在写出新代码之前，就在块头里知道这一段改了多少行。把代码写进 JSON（相对 Markdown）还要额外转义换行和引号。

决定工具格式时，他们的建议是：

- 给模型足够的 token 去「想」，再让它把自己写进死角。
- 让格式接近模型在互联网文本里自然见过的样子。
- 确保没有格式上的「开销」，例如要准确数清成千上万行代码，或对自己写的代码做字符串转义。

一条经验法则：想想人机界面（HCI）投入了多少功夫，并计划在做好的 Agent–计算机界面（ACI）上投入同样多的功夫。一些做法：

- 站在模型的位置。根据描述和参数，这个工具怎么用是否一目了然，还是得仔细想？如果是后者，对模型多半也一样。好的工具定义常常包括用法示例、边界情况、输入格式要求，以及和其他工具的清晰边界。
- 怎样改参数名或描述，才能让事情更明显？把它当成给团队里初级开发者写一份好的 docstring。工具很多、又彼此相似时，这一点尤其重要。
- 测试模型如何使用你的工具：在 workbench 里跑很多示例输入，看模型犯什么错，再迭代。
- 给工具做 poka-yoke（防错）。改参数，让犯错变得更难。

做 SWE-bench 的 Agent 时，他们花在优化工具上的时间，实际上超过了优化整体提示。例如，Agent 离开根目录之后，使用相对路径的工具会让模型出错。修法是让工具始终要求绝对路径——之后模型用这个方式就没有问题了。
